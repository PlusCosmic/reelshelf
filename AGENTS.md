# AGENTS.md

## Repo Shape

- `api/` is the .NET 10 ASP.NET API; real startup and endpoint wiring live in `api/Program.cs`.
- `frontend/` is the Bun workspace React 19/Vite/TanStack Router app; app entry is `frontend/src/main.tsx` and routes live under `frontend/src/routes/`.
- `migrations/` is a separate .NET 10 Evolve migration runner; the API does not run migrations on startup.
- `desktop/` is the Windows desktop app (the uploader, ADR-0010), in Rust: the Cargo workspace `desktop/Cargo.toml`, separate from `Reelshelf.sln` and the Bun workspace (toolchain pinned in `desktop/rust-toolchain.toml`, Rune pinned to one `dev` revision in `[workspace.dependencies]`), with `desktop/core` (`reelshelf-core`, no UI and no Windows APIs), `desktop/api` (`reelshelf-api`, the HTTP client) and `desktop/app` (`reelshelf-app`, the Rune app, binary `reelshelf`, packaged as `Reelshelf.exe`); `desktop/package/` holds the MSIX manifest, its assets and `package.ps1`. CI's `Desktop` job runs `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` there on Linux (the app's headless checks on lavapipe, uploading every scene's render), and its `Windows uploader` job lints `reelshelf-app` for `x86_64-pc-windows-msvc` and builds the MSIX.
- `desktop/monitor` (`reelshelf-monitor`, binary `reelshelf-monitor`) is the Mac monitoring app in the same Cargo workspace: a Rune window (rune-kit's split view, the uploader's theme through `reelshelf_app::theme`, words in its `copy.rs`). It signs in to Reelshelf with the device flow as the monitor (`client: "monitor"`, `X-Reelshelf-Client: monitor/<version>`, the token in the macOS Keychain, memory on Linux; `session.rs`) and shows Overview, Storage, Transcoding and AI pipelines from `/api/admin/ops/*`, polling the section showing every 30 s; its Dashboards section reads Grafana only (`/api/search`, `/api/dashboards/uid/{uid}`, `POST /api/ds/query`, with the address and a Viewer token entered in Settings and kept in the Keychain, or `GRAFANA_URL`/`GRAFANA_TOKEN` in debug builds) and draws Prometheus time series and stat panels natively, linking other panels to Grafana; `REELSHELF_MONITOR_FIXTURES=1` runs it on fixture data, and `tests/scenes.rs` renders it light and dark (`desktop/monitor/README.md`).
- `workers/Reelshelf.Worker/` is the transcode worker, a .NET 10 console app with its own `Dockerfile`; its tests are `tests/Reelshelf.Worker.Test/`.
- `tools/` holds operator tools that build with `Reelshelf.sln` but ship in no image: `tools/Reelshelf.StorageCheck/`, the storage preflight (below); its tests are in `tests/Reelshelf.Test/StorageCheck/`.
- Every word the frontend shows people lives in `frontend/src/copy/`, one module per area (`landingCopy`, `libraryCopy`, ...; conventions in its `README.md`), so copy is reviewed and changed in one place. The `reelshelf/no-jsx-copy` lint rule (`@pluscosmic/ui`'s `no-jsx-copy`, from `@pluscosmic/ui/eslint`) fails on words written straight into JSX outside that folder (text, strings in `{...}`, and readable attributes such as `aria-label`, `title`, `placeholder`); tests are exempt. Plan limits the signed-out pages and terms quote come from `copy/planLimits.ts`, which mirrors `TierLimits`. API messages and emails are still written in `api/`.
- Docs, ADRs and runbooks live in the private [`PlusCosmic/reelshelf-docs`](https://github.com/PlusCosmic/reelshelf-docs) repo, cloned next to this checkout (`../reelshelf-docs`); a `reelshelf-docs/...` path anywhere here means a file there. Only the README's screenshots stay in `docs/screenshots/`. Migration comments still say `docs/...` because editing an applied migration breaks Evolve's checksum.
- `frontend/src/api-client/` and `frontend/src/routeTree.gen.ts` are generated and committed; do not hand-edit them.
- This repository is public. Nothing committed here (docs, ADRs, comments, commit messages, PRs, issues) mentions the operator's personal circumstances: where they live or might move, their legal or business status, or their finances. A choice is explained by its engineering reasons. ADRs and design docs describe the plan being built and how it works, with at most a short "Considered" section at the end; they don't list options not being pursued or ideas for later.

## Commands

- Install with `bun install` from the repo root; this repo pins `bun@1.3.13` in `package.json`.
- Root verification: `bun run check` runs `build -> typecheck -> lint -> test -> format:check`.
- Focused frontend checks: `bun run build`, `bun run typecheck`, `bun run lint`, `bun run test` from root delegate into `frontend/`.
- API build: `bun run build:api` or `dotnet build Reelshelf.sln --disable-build-servers -maxcpucount:1`.
- Prefer the existing dev runner in `~/dev/infrastructure/services/clips-dev.yml` for live development instead of manually running the frontend and API.
- The frontend test script is Vitest with `--passWithNoTests`; it runs every `*.test.ts(x)` under `frontend/src/` (e.g. `utils/s3MultipartUpload.test.ts`).

## Generated Code

- After API contract changes, run `bun run generate:api-client`; it builds the API with `ASPNETCORE_ENVIRONMENT=OpenApi` and regenerates `frontend/src/api-client/`.
- Check committed client drift with `bun run check:api-client-drift`.
- TanStack Router generates `frontend/src/routeTree.gen.ts` from files in `frontend/src/routes/`; edit route files, not the generated tree.

## Local Dev Quirks

- `clips-dev` bind-mounts this repo, runs `dotnet watch` plus the Vite frontend, exposes Vite on `5173`, and routes `/api` and `/auth` to the local API process.
- The dev runner passes `--host 0.0.0.0` to Vite; do not reintroduce a hard-coded local dev hostname in `frontend/vite.config.ts`.
- Frontend API clients default to same-origin requests; set `VITE_API_BASE_URL` only for split frontend/backend deployments.
- `clips-dev` has its own database, a one-off copy of prod with its own R2 bucket (`scripts/dev-db/README.md`), and migrates it to the checkout's migrations when it starts. A migration edited after dev applied it fails Evolve's checksum check there; fix the dev database rather than the check.
- API config uses `DatabaseConnectionString` or `ConnectionStrings__DatabaseConnectionString`; Redis defaults to `localhost:6379` if unset.

## Migrations

- Run migrations explicitly with `DatabaseConnectionString="Host=...;Database=...;Username=...;Password=..." bun run migrate`.
- First-time adoption for an existing production database is `bun run migrate:adopt-existing`; it records baseline `V16` without executing the baseline SQL.
- Normal migration runs refuse a non-empty database with no Evolve `changelog`; do not bypass this safety in code changes.
- New SQL migrations belong in `migrations/db/migrations/` using Evolve names such as `V17__game_category_igdb_assets.sql`.

## API Conventions

- JSON is configured as `snake_case` in `api/Program.cs`; generated TypeScript clients reflect that contract.
- Auth endpoints are intentionally at root `/auth` for OAuth callback compatibility; other API endpoints are grouped under `/api`.
- Access lives in the database (ADR-0008, `reelshelf-docs/accounts-and-access.md`); there is no whitelist file and sign-in is open to any Discord or Twitch account. `app_user.role` (`Viewer`, `Editor`, `Admin`; new accounts get Editor) is the only source of an account's role, and its default permissions are in `Permissions.cs`, checked by `RequirePermission`. `app_user.granted_tier` (`plus`, `pro` or `unlimited`, V50) is a tier an admin gave the account. Only `AccountAccessService` (through `AccountAccessStatements`) writes either, recording each change in `account_access_change` with who and why; an admin can't change their own role and the last Admin can't be demoted (409). Admins manage both at `/admin/accounts` (`/api/admin/accounts`, `admin.users`). V50 seeded both from the old whitelist and turned `user_additional_permission` admins into Admins; V67 dropped `role_from_whitelist` and `user_additional_permission`. A fresh database's first Admin is set by hand (the SQL is in `reelshelf-docs/accounts-and-access.md`).
- Paid plans (`api/Billing/`, ADR-0007, setup in `reelshelf-docs/billing.md`) are sold through Stripe Managed Payments, so Stripe (as Link) is the merchant of record and every subscription starts in Checkout. An account's `AccountTier` (Free, Plus, Pro, Unlimited) is never stored: `AccountTierService` gives the better of the account's `granted_tier` and the best tier among its `billing_subscription` rows that are `active`, `trialing` or `past_due`, else Free; `/api/me/plan` names a granted tier (`granted_tier`) and Settings shows it as granted. Tiers limit clips, not bytes (`api/Plans/`, `TierLimits`): Free keeps 100 clips of up to 60 s, Plus 1,000 and Pro 5,000 of up to 120 s, Unlimited no limit, and each may add twice its clip limit in 30 days, counted from `clip_creation` (V46), which deleting a clip doesn't undo; the terms call this a fair use limit and Settings doesn't show it. `ClipService.CreateClip` enforces the count, the 30-day count and a byte backstop (`Storage:BackstopBytes`, 1 TiB, never for Unlimited) through `AccountPlanService`, before and under the owner's `clip-storage:` lock, and records the creation in the reservation's transaction (a reservation given back forgets it); refusals are 403 `PlanLimitExceededException`. The length cap is checked with a second's tolerance when an R2 upload completes (the probe's duration; 422 and `upload_failed` like any other probe failure) and from Twitch's reported length on import. `ClipLimitWarningService` sends the "library nearly full" mail at `Storage:WarnAtPercent` of the clip limit (the marker is still `storage_warned_at`). `GET /api/me/plan` (`AccountPlanResponse`) and `GET /api/plans` (every tier's limits, with the paid ones' Stripe prices cached 10 minutes) feed Settings → Plan (`PlanSettings.tsx`), which upgrades through Checkout and returns to `/settings?billing=success`, polling the plan for one fixed 30 s window until a current subscription for the price this tab bought (kept in sessionStorage) shows up, never taking a granted tier or a lapsed subscription for it (`components/Reelshelf/billingReturn.ts`: `waiting`, `confirmed` or `timedOut`); the uploader refuses a file longer than the plan keeps before uploading it (`utils/clipLength.ts`). Going over the limit (V47): where `Plans:Enforce` is on (off by default, since it deletes clips), `OverLimitSweeper` runs hourly (`OverLimitSweepService`, never in `OpenApi`) over accounts with more clips than Free keeps or a running grace. An account over its tier's limit starts a grace (`app_user.over_limit_since`, mailed), is mailed again `Plans:GraceWarningBefore` (3 days) before it ends, and when `Plans:GracePeriod` (14 days) is up its clips over the limit get a `grace_ended` export and are deleted through `ClipService.DeleteClip` only once that export is ready (a failed one deletes nothing); back under its limit by any route ends the grace. Clips kept are the ones the owner picked (`clip.kept_at`, `PUT /api/clips/{id}/keep`; binning a clip clears its pick and a binned clip can't be picked, V59), then the newest (`OverLimit.Split`). `PlanEndingNotifier` mails the owner when the webhook first sees a subscription set to end and they have more clips than Free keeps. Exports (`clip_export`) are made by the API, not the workers (a `transcode_run` belongs to one clip): `ClipExportProcessor` (run by `ClipExportBackgroundService`) claims one at a time (heartbeat, re-claimed after `ExportStaleAfter`, `ExportMaxAttempts` 3, a run that went quiet counting as an attempt, so the claim fails an export out of attempts instead of taking it), reads clips' `av1.mp4` through presigned GETs and writes stored zips under 4 GiB through a pipe into `R2Storage.UploadAsync` at `exports/{userId}/{exportId}/{leaseId}/reelshelf-clips-{n}.zip`, kept `ExportRetention` (28 days) and then deleted (the bucket's `exports/` rule is the backstop); exports need R2. Each claim gives the export a new `lease_id` (V58), and heartbeats, completion and failure count only from the run holding it while the export is `running`, so a run that was re-claimed stops, deletes only its own `{leaseId}/` folder and can't turn a `ready` export back or delete its parts; a ready export keeps the lease naming its parts (exports made before V58 have none and their parts sit directly under `{exportId}/`). One export per account and reason may be `pending` or `running` (`clip_export_active_idx`): `Create` answers null on a conflict, which `POST /api/me/exports` turns into 409 and the sweeper leaves for its next pass. `/plan` lists the clips over the limit, picked clips and exports; `POST /api/me/exports` asks for one of the clips over the limit, and each part is a plain link to `GET /api/me/exports/{id}/parts/{n}`, a `no-store` redirect to a 10-minute presigned GET. `POST /api/billing/checkout` takes a price lookup key (`BillingPlans`: `plus_monthly`, `plus_yearly`, `pro_monthly`, `pro_yearly`; prices are found by key, never by Stripe id) and answers the Checkout URL, or 409 while the account has an open subscription; under a per-account advisory lock it first reads the account's last Checkout Session (`app_user.stripe_checkout_session_id`, V48) from Stripe, expiring it if still open and recording a completed one's subscription at once (409 if that is open), so neither a second tab nor the webhook's lag allows a second subscription; `POST /api/billing/portal` opens the Customer Portal (the default configuration, which doesn't switch plans). Subscribers change plan from Settings' cards through `POST /api/billing/plan`: an upgrade (higher tier, or yearly from monthly) answers a portal session opened on `subscription_update_confirm` under `Billing:PlanChangePortalConfiguration` (unset hides plan changes; `can_change_plan` on `/api/me/plan`), charged prorated at once; a downgrade waits for the period's end through a subscription schedule the API attaches (`StripeBilling.ScheduleDowngradeAsync`, released once the change starts), recorded as `billing_subscription.scheduled_lookup_key`/`scheduled_at` (V49, read from the schedule's next phase when the subscription is synced; `subscription_schedule.*` webhooks sync it too), and `DELETE /api/billing/plan/scheduled` drops it. The portal can't delay downgrades across products, hence the API's own schedule. `POST /api/billing/webhook` (anonymous, out of the OpenAPI document) checks Stripe's signature, then reads the subscription the event names from Stripe again and upserts it, never trusting the event's copy, so order and repeats don't matter; every sync (the webhook, checkout's settling, plan changes) reads and upserts under a transaction-scoped advisory lock on the subscription id (`IBillingStore.LockSubscription`, joining the checkout lock's transaction when inside it), so an older read never commits over a newer one, and the upsert never moves a recorded subscription to another account (a mismatch is logged). `StripeBilling` is the only code that talks to Stripe. Billing is off (404s, everyone Free or on their granted tier) without `Billing:SecretKey`, a restricted key; with it, `Billing:WebhookSecret` is required at startup. Buying is behind the `paid-plans` feature flag (the first one): while it is off for an account, checkout and `POST /api/billing/plan` answer 404, `/api/plans` carries no prices, and `/api/me/plan`'s `billing_enabled` and `can_change_plan` are false (the uploader's upgrade hint follows `billing_enabled`), while `can_manage_billing`, the portal, Keep and the webhook stay, so a subscriber keeps managing their plan; dev needs `FeatureFlags__Overrides__paid-plans=true` (`reelshelf-docs/billing.md`).
- Feature flags (ADR-0009, `api/FeatureFlags/`, runbook in `reelshelf-docs/feature-flags.md`) roll features out to named accounts, a role, a tier, granted testers or a percentage, and switch them off, without a deploy; they never grant access, so a Pro-only feature still checks the tier and an admin page its permission. Code asks `FeatureFlagService` (scoped: `IsEnabledAsync(key, user)`, `IsEnabledAsync(key, accountId)` outside a request, `GetEnabledAsync(user)`), and an endpoint behind a flag carries `RequireFeature(key)` (404 while off). Keys are constants in `FeatureFlagKeys` (and `All`), mirrored by `featureFlagKeys` in `frontend/src/shared/services/featureFlags.ts`, and removed with their checks once a feature is out to everyone. `FeatureFlags:Overrides:<key>` (`true`/`false`) wins on that instance; dev, local runs and tests use it, prod sets none. Everything else goes to PostHog, only where `PostHog:ProjectToken` and `PostHog:SecretKey` (a Project Secret API Key, which local evaluation needs) are set (prod alone: the free plan has one project; a token without the secret key fails startup, `PostHogSettings`). The `PostHog` client evaluates locally only (`PostHogFeatureFlagEvaluator`: `OnlyEvaluateLocally`, no `$feature_flag_called` events, no GeoIP) from definitions it downloads every `PostHog:FeatureFlagPollInterval` (default 5 min, about 86,400 of the free plan's million flag requests a month, so a change in PostHog takes up to 5 minutes), on `PostHog:HostUrl` (default `https://eu.i.posthog.com`; the SDK's default is the US host). The distinct id is the account id and the person properties are `role`, `tier` and `granted_tier` (`none` without one), worked out from the database on every check, so a flag never waits on PostHog. So that PostHog's UI lists those properties and shows who a flag matches, `PostHogPersonSyncService` (only where PostHog is configured and `PostHog:ProjectId` and `PostHog:PersonalApiKey`, a Personal API Key with `person:write`, are set, so the people can be deleted; without them a startup warning says the sync is off; never in `OpenApi`) identifies each account to PostHog as a person with just those three properties: at startup, every `PostHog:PersonSyncInterval` (15 min) and when `AccountAccessService` changes a role or granted tier (`PostHogPersonSyncSignal`), sending only accounts whose properties differ from what `posthog_person` (V64) records was last sent, as `$identify` events through `/batch/` (`PostHogPeopleClient`, plain HTTP, since the SDK's identify swallows failures). Account deletion deletes the person (`persons/bulk_delete` on `PostHog:ApiHostUrl`, default `https://eu.posthog.com`, with the Personal API Key, since a Project Secret API Key can't touch people) before the account row, retrying on the next pass if PostHog refuses. Nothing else about an account is sent. Without PostHog, or when it fails, a flag is off. `GET /api/me/features` (`FeatureFlagsResponse.enabled`) lists the known flags on for the caller, and `useFeature(key)` (`hooks/featureFlags.queries.ts`) reads it, false until loaded; it is for the signed-in app only, never the landing page.
- Sign-in providers are Discord, Twitch and Google (`DiscordClientId`/`DiscordClientSecret`, `TwitchClientId`/`TwitchClientSecret`, `GoogleClientId`/`GoogleClientSecret`; Google's OAuth client redirects to `/auth/google/callback`). Accounts live in `app_user`; each provider login is a `user_identity` row, and one account may link one of each. All six credentials are required: the API throws on startup when any is missing or blank, so a misconfigured deployment fails immediately instead of returning a 500 from `/auth/{provider}/login`. The `OpenApi` environment is exempt because document generation builds the app without secrets. IGDB game search uses the same Twitch application's credentials (IGDB has none of its own), so there are no separate IGDB settings. Google has no usernames (`AuthProvider.ProvidesUsername`): a Google identity's `username` is its address, and the account's username never comes from it; a new Google account starts with one made from its name (`Usernames.Suggest`), its owner confirms or changes it on first sign-in (`needs_username`), and an account whose primary identity is Google, or whose owner has chosen one (`app_user.username_chosen_at`, V53), sets it with `PUT /api/me/username` (`Usernames`: 2 to 32 of `a-z0-9_.`, not another account's, ignoring case, 409 otherwise); provider sign-ins never overwrite a chosen username. Every account needs an email address: `needs_onboarding` stays true until `app_user.email` is set (accounts that skipped it before are asked again), `PUT /api/me/email` refuses an empty one, and the onboarding step prefills the one a provider reported. The Discord Activity only knows Discord identities, so an account without one joins it as a guest. See `reelshelf-docs/adr/0003-linked-identities.md`.
- Device tokens (ADR-0010, `api/Devices/`, V63; spec in `reelshelf-docs/desktop-uploader/README.md`) let the desktop uploader act for an account without the site cookie, through a flow modelled on RFC 8628. The app calls `POST /api/devices/authorize` (anonymous, `device-authorize` rate limit, 10/min per address) with a `device_name` and an optional `client` (`uploader`, the default when left out so the shipped uploader is unchanged, or `monitor` for the macOS monitor app; anything else is 400; `DeviceClients`) and gets a `device_code` (32 random bytes, base64url), a `user_code` (8 letters of `DeviceCodes.UserCodeAlphabet`, shown `XXXX-XXXX`, matched ignoring case and the dash), `verification_uri` (`FrontendOrigin` + `/device`), `verification_uri_complete`, `interval` (`Devices:PollInterval`, 5 s) and `expires_in` (`Devices:CodeLifetime`, 10 minutes). The owner decides on `/device`, which says which app is asking (`GET /api/devices/authorize/{user_code}` carries `client`; `.../approve`, `.../deny`: cookie, `clips.create`, 404 unknown or expired, 409 already decided) while the app polls `POST /api/devices/token` (anonymous, `device-token`, 30/min per address), which answers 400 `{ error }` with `authorization_pending`, `slow_down` (polled within the interval; every poll moves `last_polled_at`), `access_denied` or `expired_token` (also for an unknown or already used code) and, once approved, creates the `device_token` with the request's `client` (V68: `client` on both tables, `NOT NULL DEFAULT 'uploader'`, so tokens issued before it and an image that doesn't know it stay the uploader's) and deletes the request in one transaction under a row lock, answering `{ access_token: "rsd_…", token_type: "Bearer" }` with `no-store`. Only SHA-256 hashes of device codes and tokens are stored (`DeviceStatements`). The `DeviceToken` scheme (`DeviceTokenAuthentication`, like `WorkerAuthentication`) reads `Authorization: Bearer rsd_…` only (never a query string or cookie; other bearers are left to their schemes), finds a token that isn't revoked whose account isn't suspended or being deleted (so both get 401), and gives a principal with `NameIdentifier` = the account, a `device_id` claim and a `device_client` claim, so `AuthenticatedUserMiddleware`, permissions, plan limits and per-account rate limits (`clip-prepare` is shared with the browser) apply unchanged; it writes `last_used_at` and `client_version` (the `X-Reelshelf-Client` header) at most once per `Devices:LastUsedPrecision` (1 h). A token works only where `.RequireAuthorization(AuthorizationPolicies.CookieOrDevice)` (cookie or `DeviceToken`) sits beside the group's own `RequireAuthorization()`, since an endpoint's policies combine: `GET /api/games/categories`, `GET /api/me/plan`, `CreateVideo`, `DeleteClip` (with a token only for the caller's clip still `awaiting_upload`, else 403), the three multipart upload endpoints, `GET /api/me` and `GET /api/me/features`; everywhere else it gets 401. The `/api/admin/accounts`, `/api/admin/reports` and `/api/admin/ops/` groups carry `AuthorizationPolicies.CookieOrMonitorDevice` instead: the cookie, or a token whose `device_client` is `monitor`, so an Admin's uploader token gets 403 there, and their permissions keep a monitor token to Admins; an admin cuts a monitor off by removing its device in Settings → Devices. `DELETE /api/devices/current` (`AuthorizationPolicies.Device`, token only) is the app's Sign out. Settings → Devices lists them with which app each is (`GET /api/me/devices`, newest first, each with `client`) and revokes them (`DELETE /api/me/devices/{id}`, cookie only, 404 for another account's), and a revoked token gets 401 at once. Every device endpoint but the anonymous two and `DELETE current` carries `RequireFeature(FeatureFlagKeys.DesktopUploader)` (`desktop-uploader`), so approving is where the flag bites; upload endpoints aren't flagged, so an issued token keeps working while it is off. `ClientVersionGate` (before authentication) answers every `/api` request whose `X-Reelshelf-Client` is `uploader/<version>` below `Uploader:MinimumVersion` (a `System.Version`, default `0.0`, an unreadable version counting as the oldest) with 426 `{ error: "client_too_old", minimum_version }`; raise it only once the version it names has been in the Store a week. `DeviceTokenSweepService` (daily, never in `OpenApi`) deletes expired requests, revokes tokens unused for `Devices:RevokeUnusedAfter` (90 days), and then deletes revoked tokens' rows, so a device's name and use are kept only while it is signed in, as the privacy policy says. Account deletion removes both tables' rows with `app_user`. The endpoint tests (`tests/Reelshelf.Test/Devices/`, `[PostgresFact]`) run the whole app (`DeviceApi`) against a schema with every migration and a fake R2.
- Ops endpoints (`api/Ops/`, for the native macOS monitor app): `GET /api/admin/ops/storage` (clips and bytes from the database by tier and the top 20 accounts, exports held, and which object store is configured, never its keys), `.../transcoding` (`transcode_run` by type over the last hour and day through `TranscodeRunMetricsSource`, the last 50 failures, the overflow pools in `Overflow:Pools` with the tasks the scaler last counted on that instance, never counted or started on request, and the AAC backfill's remainder) and `.../ai` (the three AI run queues through `RunTableMetricsSource`, their last 50 failures, and runs, tokens and legend detection's cost by model over a day and 30 days) are read-only, `admin.ops` (Admins), `CookieOrMonitorDevice` (the cookie or the monitor app's token) and behind `ops-monitor`, each answer cached 15 s in memory (`OpsSnapshotCache`); they call no cloud API.
- The desktop uploader (`desktop/`, ADR-0010, spec `reelshelf-docs/desktop-uploader/README.md`, screens `screens.html`) is a Windows tray app in Rust, shipped as a full-trust MSIX through the Microsoft Store, that watches one recordings folder and uploads new clips with a device token. It talks only to the `CookieOrDevice` endpoints, through `reelshelf-api` (`ApiClient`, one async method per endpoint, its types in `types.rs`), whose `tests/contract.rs` checks every call, request and response type against `frontend/src/api-client/Reelshelf.json` (kept current by `check:api-client-drift`), so an API change that would break the app fails `cargo test` and an endpoint the app uses is changed backwards compatibly or the app is told to update; every request carries `X-Reelshelf-Client: uploader/<version>`, the version compiled in from `REELSHELF_APP_VERSION` (which `package.ps1` sets) else the crate's. Release builds use `https://reelshelf.app`; debug builds read `REELSHELF_API_BASE_URL` (`links.rs`). `reelshelf-core` does everything but the UI and the Windows parts, which sit behind `CredentialStore`, `GameActivity`, `Notifier`, `Startup` and `Clock` (`platform.rs`), with the API behind `UploaderApi` (the app's `api_adapter.rs` maps 401 to signed out and 426 to update required): settings and the SQLite ledger under `%LOCALAPPDATA%\Reelshelf\Uploader` (`settings.json`, `ledger.db`, the .NET build's schema and encodings so an installed copy keeps both, `logs\uploader-YYYYMMDD.log` kept 14 days, `logs.rs`, which redacts anything shaped like a token); `FolderMonitor` baselines a newly chosen folder (those files are never uploaded), takes `notify` events only as hints (`watcher.rs`), rescans every 60 s and on overflow, and settles a file once its size and last-write time hold 5 s and it opens for reading; the ledger keys files by recordings folder, path, size and last-write time (to the millisecond) so nothing is hashed or uploaded twice; `matching.rs` (a port of the frontend's `assignGame`/`normalizeForMatch`, with `dates.rs` porting `deriveCreatedAt`) matches the first folder below the root, a saved folder choice winning, then the default book, else `needs_book` (S3); `UploadPipeline` checks the `mvhd` length of MP4/MOV (`media.rs`) against `max_clip_seconds` plus a second, hashes MD5, prepares (409 `duplicate`, 403 titled "Plan Limit Reached" `plan_full` and uploads pause, rechecked every 30 minutes, 404 back to `needs_book`), refuses any protocol but `s3-multipart` (the clip is deleted and the tray asks for an update), and `MultipartUploader` sends one part at a time to presigned URLs asked for 10 at a time (never with the token), retrying each after 1, 2, 4 and 8 s and saving each ETag to the ledger, resuming from `GET .../upload/parts` (a gone upload deletes its clip and starts again); completing answers 422 `too_long` when about length else `failed`, 503 retries in a minute; network errors and 5xx back off 15 s doubling to 5 minutes, 5 attempts a file, and `failed` files get one more try at the next start. A `TokenBucket` limits part bodies to the speed limit; while `GameActivity` reports a full-screen game a clip that hasn't started waits (or, with "Upload slowly", goes at the limit or 5 Mbit/s), and one uploading waits after its current part. `UploaderEngine` runs it all and works out `UploaderState` (T1–T8 by the priority T8 > T6 > T7 > T5 > T4 > T3 > T2 > T1, with both lines' words) and the notifications N1–N5 with their buttons; the app only renders it. - Apex legend detection (`api/ApexLegends/LegendDetection/`) sends the embedded prompt, schema and reference sheet in `Resources/` to a vision model via Microsoft.Extensions.AI, with each of the clip's six thumbnails as a half-resolution overview plus an enlarged close-up of the bottom-left HUD panel, both made with ffmpeg (`LegendHudCropper`; CI installs ffmpeg for its tests). Runs are queued in `legend_detection_run` and processed by a background service (pending → running → succeeded/failed, a CHECK constraint since V57). As in transcription and summaries, a claim takes a pending run past its retry delay or a running one whose `started_at` is older than `StaleAfter`, first failing those with `MaxAttempts` used, and sets a fresh `claim_id` (V57); complete and fail write only while the run is still `running` under that claim, so a slow processor's late result after a reclaim, or a failure after a success, is dropped and logged. A retryable failure of a run archived meanwhile ("Start fresh") fails it rather than leaving an archived pending run, and an archived run's late answer never escalates; nothing runs until `LegendDetection:Model` and `LegendDetection:Providers:<provider>:ApiKey` are set, and `LegendDetection:AutoDetect` queues a run when an Apex clip finishes encoding. Each run records its reasoning effort (`LegendDetection:ReasoningEffort` by default, or chosen on `/legend-detection`), and each API instance processes `LegendDetection:Concurrency` runs at once (default 4; dev and prod each have their own queue but share the provider's rate limit). `LegendDetection:EscalationModel` (off when empty) queues an `escalation` run with a stronger model on the same provider when an automatic run sees the owner's HUD but returns no legend or one below `EscalateBelow` (default 0.9); manual and escalation runs are claimed before automatic ones. Each instance escalates by its own config, so set it on dev and prod alike; `LegendDetection:EscalationProvider` escalates to another provider (empty keeps the run's own). New providers are a case in `LegendRecognizerFactory`. The `openai-decisions` provider is OpenAI's Decisions API (`DecisionsLegendRecognizer`, plain HTTP since the .NET SDK lacks it, in public beta): it reuses the `openai` key, defaults to `gpt-6-luna`, takes no reasoning effort, sends `Resources/decisions-prompt.md` with the same images, and asks a `hud_detected` predicate and a `legend` choice over `ApexLegendNames` plus `unidentifiable`; the legend's confidence is the probability the API gives the chosen option. Its prompt version is hashed separately (`DecisionsPromptVersion`). The `openrouter-decisions` provider (`OpenRouterDecisionsLegendRecognizer`) asks the same two questions of a decisions model on OpenRouter's Decisions API (`/api/alpha/decisions`), with the `openrouter` key and `typesafe/jev-1.14` (TypeSafe's Jev) by default; Jev takes images of 256 to 1,568 pixels a side (and at least 78,400 pixels), so it gets the reference sheet in halves (`LegendDetectionResources.ReferenceSheetHalvesAsync`, ffmpeg) and every screenshot fitted to those bounds (`LegendHudCropper.FitAsync`), since the close-up of a 1440p or 4K frame is too wide and that of a low-resolution frame too short. The `anthropic` provider (`AnthropicLegendRecognizer`, official `Anthropic` SDK) sends the chat prompt and schema to Claude (e.g. `claude-sonnet-5-5`, `claude-haiku-5-5`) with the halved sheet, a cache breakpoint after it, and the effort as `output_config.effort` (`none`/`minimal` fail the run); it asks for no refusal fallback, so a run's answer always comes from the model it names. Each has its own prompt version. `/legend-detection/evals` compares models: an eval (`legend_eval`) queues one `eval`-trigger run of a provider, model and effort on every labelled clip. Eval runs are claimed after every other run, are never archived by "Start fresh", and are left out of a clip's current legend (the review list, the baseline and clip summaries), so they never change what Reelshelf shows. Evals are scored against the labels as they are when read (failed runs count as wrong) and costed from the provider's billed cost (`cost_usd`, which OpenRouter reports) or from `legend_model_price`, prices per million tokens set on the page, so fixing a label or a price re-scores or re-costs every eval. Latency is the model call alone. The page's cascade panel works out production's escalation from two finished evals (`GET /api/legend-detection/evals/cascade`): the first eval's answer, or the second's where production would escalate (succeeded, HUD seen, no legend or one below the threshold), with accuracy, cost and mean time at each threshold, without running anything again. `/legend-detection/baseline` labels every Apex clip's owner's legend quickly: clips are grouped by their answer (the label, else the latest succeeded run), shown as HUD close-ups cut from the thumbnails with CSS and with portraits cut from the reference sheet (`GET /api/legend-detection/reference-sheet`, so its legends must stay in `ApexLegendNames` order, half on each of two rows); fixing a clip saves its label at once and confirming a group saves the rest through `PUT /api/legend-detection/labels`. Owners see it too: the `Clip` contract's `legend` is an Apex clip's label, else its latest succeeded run outside evals and archives (`ClipsStatements.PlayerLegendSql`, canonicalized by `ApexLegendNames`), null for other games, and the frontend shows it with a portrait from `frontend/public/apex-legends/<legend-slug>.png` (`legendPortraitUrl`; every name in `ApexLegendNames` needs one, which `ClipLegendTests` checks) as its own column in one game's clip list (never beside the game column of a mixed list; in the meta line beside the player and on phones) and as "Played as" on the clip's page. The Apex book alone filters by legend, in the database: `GET /api/clips?legend=` (any spelling `ApexLegendNames` recognizes, else 400) keeps the clips whose legend is that one by the same rule, so paging covers every match, and `GET /api/clips/legends` counts the owner's Apex clips per legend for the picker beside the search (`LegendPicker`: a grid of portraits, most played first, a bottom sheet on phones).
- Clip videos go through `IClipVideoHost` (`api/Video/`): create, server-side upload, fetch, delete. Each clip records the host holding its video in `clip.video_host` (`r2`, `VideoHostNames`, check constraint from V39, `r2` only since V62), and every per-clip call goes to that host through `ClipVideoHosts`; hosts are keyed services registered by name with `AddClipVideoHost<THost, TMediaUrls>` in `ReelshelfApiConfiguration`, which is all adding one takes (plus its name in the constraint). Every new clip goes to `r2`, so startup fails outside the `OpenApi` environment when the `r2` host isn't registered (`AddClipVideoHostRouting`). Bunny Stream, the first host, is gone: every clip moved to R2 and V62 refuses a database that still has one on Bunny. V67 dropped its columns (`clip.video_status`, `bunny_video_id`, `migrated_at`, `filed_category_id`) and tables (`clip_collection`, `clip_collection_merge`). `CreateVideoAsync` gets the reserved clip's id. The `r2` host (`api/Video/R2/`, #212) is our own pipeline: an S3 bucket through AWSSDK.S3 with S3-compatible calls only (`R2Storage`), registered by `AddR2VideoHost` only when the object store is configured (`R2Options`): `Storage:AccessKeyId`, `SecretAccessKey`, `Bucket`, `MediaBaseUrl` (the media domain's https origin, never `r2.dev`) and either `Storage:Region` alone (AWS S3, virtual-hosted) or `Storage:Endpoint` (an S3-compatible https endpoint such as R2's, path-style, signed for `Storage:Region` or `auto`), or else the older `R2:AccountId`, `AccessKeyId`, `SecretAccessKey`, `Bucket` and `MediaBaseUrl` (R2, region `auto`); a partial section, or both sections, fails startup (`Storage`'s `BackstopBytes` and `WarnAtPercent` don't count). Dev and prod have separate buckets. An R2 clip's video id is its clip id; the source goes to `uploads/{clipId}` and outputs to `clips/{clipId}/v{n}/` (`av1.mp4`, `thumbnail.jpg`, `thumbnail_1..5.jpg`, `preview.mp4`; `R2ObjectKeys`), with the clip's current version, codecs and height in `clip.video_version`, `video_codecs` and `video_height` (V42). R2 has no video object: `GetVideoAsync` answers from the clip row, and delete removes `uploads/{clipId}` and `clips/{clipId}/`. `UploadAsync` (Twitch import) streams to `uploads/{clipId}` (one PUT, or 8 MiB multipart parts, aborted on failure) and then marks the clip `uploaded` and enqueues its `transcode` in one transaction. Browser uploads to R2 (#213) are presigned S3 multipart uploads: `CreateUploadTargetAsync` (which gets the reserved file size) starts one on `uploads/{clipId}` and returns protocol `s3-multipart`, the endpoint `/api/clips/videos/{clipId}/upload` and `multipart` (`upload_id`, `part_size`, `part_count`; `MultipartUploadParts`: 8 MiB parts, larger in whole MiB when a file would need more than 10,000, so any declarable size fits). R2's `R2VideoHost` implements `IMultipartUploadHost`, and `MultipartUploadEndpoints` (owner-only, each with `RequireAuthorization()` and `clips.create`; any other caller or host gets 404) offers `POST .../upload/parts` (up to 100 part URLs per call, part numbers 1 to `part_count`, each a 1-hour presigned PUT signing only the host), `GET .../upload/parts?uploadId=` (the parts R2 holds, for resuming) and `POST .../upload/complete` (every part with its ETag; rate-limited with clip preparation). Completing joins the parts, requires the object to be exactly the reserved `file_size` (so the quota holds), and runs a cheap ffprobe (`FfprobeUploadProbe`, 30 s timeout) over a 10-minute presigned GET: no video stream, no picture size, no duration or an unreadable file marks the clip `upload_failed`, deletes the object and answers 422 with the reason; a probe that times out or can't read from storage answers 503 and leaves the clip waiting, and completing again picks up the joined object. HDR and variable frame rate are left to the worker. A passing file goes through the same mark-`uploaded`-and-enqueue transaction as `UploadAsync`, and repeating a completion is accepted. The plan's limits and the MD5 duplicate check (403/409) stay at preparation in `ClipService.CreateClip`, the same for both hosts. Before that, the uploader (`UploadsProvider`) hashes files ahead of its 3 upload slots, in up to 4 Web Workers (`utils/fileHash.ts`, hash-wasm), and asks `POST /api/clips/categories/{id}/videos/duplicates` (up to 500 hashes, batched per book by `utils/duplicateCheck.ts`) which it already has, so a folder's duplicates are turned away without preparing a clip each; a file with a saved R2 upload skips that check to resume. No upload id is stored: deleting an R2 clip (the uploader's cancel, the abandoned-upload purge, account deletion) first aborts any open multipart upload on its key (`ListMultipartUploads` by prefix), and the bucket's lifecycle rule aborts what is left after a day. The browser side is `frontend/src/utils/s3MultipartUpload.ts` (hand-written, no Uppy): 4 parts at once, URLs asked for 10 at a time, each part retried with backoff, progress per finished part, and the clip, upload id and finished parts' ETags kept in localStorage under the book, MD5 and size, so dropping the same file on the same book after a reload resumes it (reconciled with the part list; a gone upload's clip is deleted and the file prepared afresh). Pausing aborts the run (its retry waits too) and resuming starts a new one, with its own signal, once the aborted one has unwound, so a quick resume always carries on; the uploader (`UploadsProvider`) pauses and resumes outside its state updaters, holds a clip still being prepared as `paused` when its upload would start, and forgets a file's place in its book (so it can be added again) once its item fails, is retried or is cleared. Downloads (`GET /api/ffmpeg/download/{videoId}`, `api/FFmpeg/`, after the usual owner-or-`UserCanAccessClip` check, 404 otherwise) go through the host's keyed `IClipVideoDownloads` (R2's `R2Downloads`; `ClipVideoHosts.DownloadsFor`, 404 for a host without one), which answers with a `no-store` 302 to a 10-minute presigned GET of the current `clips/{clipId}/v{n}/av1.mp4` carrying `response-content-disposition: attachment; filename="<title>.mp4"; filename*=UTF-8''<title>.mp4` (the title cleaned by `DownloadFileName`, the quoted name ASCII-only), and only for `ready` clips (404 before). The download button is a plain link, never fetch, so the browser follows the redirect without CORS on the bucket. Bucket lifecycle rules, CORS, caching and the presigned URL contract are in `reelshelf-docs/video-pipeline/r2-bucket.md`. Before the API is pointed at a new store, run the storage preflight (`tools/Reelshelf.StorageCheck`, usage in its `README.md`): it runs this code, the worker's `MediaTransfer` and the CDN purge against the real buckets and distribution under fresh random keys, reading only `Storage:*` and the two `Moderation` settings from the environment (so `R2__*` beside them is ignored), then deletes everything it wrote and lists again to prove it. The `Clip` contract's `video` is the app's own `ClipVideo` (`api/Core/Models/Clip.cs`). Every media URL (thumbnail, playback sources, the server-side stream ffmpeg reads, detection frames) is built by `ClipMediaUrls` (`api/Core/`) from the clip's `ClipVideoRef` (`video_host`, `video_id`, `video_version`, `video_codecs`, `video_height`, `video_state`, plus `thumbnails_ready` from `ClipVideoColumns.ThumbnailsReadySql`; rows that show media implement `IClipVideoColumns` and select all seven, and a row missing `video_state` reads as `awaiting_upload`, so it hands out nothing) and that host's `IClipVideoMediaUrls` (`R2MediaUrls` on `R2:MediaBaseUrl`), and handed out on the responses that show a clip (`ClipVideo`, shared clips, collection previews, legend detection and transcription review); the frontend builds none, except the Discord Activity's paths in `frontend/src/shared/utils/clipMediaUrls.ts` (`/media` for R2), which must go through Discord's URL Mappings. Nothing hands out a URL before its file exists (#229), since the browser never retries a failed `<img>` and Cloudflare caches R2's header-less 404 for its default 3 minutes: `sources` are `[]` until the clip is `ready`, and its thumbnail (`thumbnail_url`, null until then) and detection frames (`[]`) wait until it is `ready` or a worker has reported `thumbnails_ready` for its current `video_version` (`transcode_run.thumbnails_ready_at`). The Activity's `ActivityMedia` carries `type` (null until ready) and `has_thumbnail` for the same reason. Players get a clip's `sources` (`PlaybackSource`: `url`, full MIME `type` with codecs, optional `height`), in the order to try them; an R2 video is one progressive AV1 MP4 (`video/mp4; codecs="..."` from the worker's reported codecs, plain `video/mp4` without them, with its height). Every player on the site (clip page, share page, legend and transcription review) is `components/Video/ClipVideoPlayer.tsx`, rendered through `ClipVideoStage` (same folder), which shows the clip's processing state instead until `video.status` is `ready`: the thumbnail once it exists (the game's cloth before), "Processing" with the encode percentage, or a message for `encode_failed` and `upload_failed` (`awaiting_upload` and `uploaded` count as processing). The legend and transcription review clips carry `video_status` for it; the share page only ever gets ready clips. An open clip that is still processing is refetched every 3 s (`useClip`), the library's pages every 5 s, and clip cards render no `<img>` until there is a thumbnail. The player itself is a native `<video controls>` fed by `attachStream` (`shared/utils/videoStream.ts`, which the Activity shares), which attaches the first source the device can play. It remembers the viewer's volume and mute in localStorage (`reelshelf.player.volume`, `shared/utils/volumePreference.ts`, which the Activity uses under its own key) for every player, and the clip page always autoplays (a browser that blocks sound without a click leaves it paused). An MP4 is checked with `navigator.mediaCapabilities.decodingInfo` (else `canPlayType`) and played as the video's own `src`; there is no HLS player. When no source can play, the player says "This clip can't play on this device", which means a `ready` clip this device can't decode and is where a fallback would plug in. There is no embed player or iframe. A clip's status is the app's own `ClipVideoStatus` (`api/Video/ClipVideoStatus.cs`), stored as text in `clip.video_state` (`awaiting_upload`, `uploaded`, `processing`, `ready`, `encode_failed`, `upload_failed`, the same spelling as `video.status` on the `Clip` contract). Only `ready` is playable. Every writer of `video_state` takes its allowed from-states from one table, `ClipVideoTransitions` (`ClipVideoStatus.cs`, #322), and a move it refuses writes none of the row, and `upload_failed` is final for an R2 upload (the uploader prepares a new clip). `ClipVideoUpdateHandler` applies the transcode worker's reports to the clip; `ClipStatusRefreshService` purges abandoned uploads.
- Transcoding (`api/Video/Transcoding/`, #208) is the queue for our own R2 + AV1 pipeline; the R2 host enqueues a `transcode` when an upload completes. Jobs are rows in `transcode_run` (type `transcode`, `thumbnails`, `trim`, `audio` or `fallback`; `pending` → `running` → `succeeded`/`failed`; `input`/`output` jsonb, `video_version`, `priority`), queued with `TranscodeQueue.EnqueueAsync`, and a clip has at most one pending or running `transcode`. Workers are a separate service and never touch Postgres: they call `POST /api/worker/claim` (204 when idle; else the job, a `lease_id`, a presigned GET `source_url` for its input and presigned PUT `upload_urls` by output file name, which sign `Content-Type` and `Cache-Control: public, max-age=31536000, immutable` and live `Transcoding:PresignLifetime` (2 hours, never less than `StaleAfter` plus an hour); both null while R2 isn't configured, through `ITranscodeStorage`), then `/api/worker/{runId}/progress` (`percent`, `thumbnails_ready`), `/complete` (`outputs`: `codecs`, `width`, `height`, `files`; `length_seconds`; `size_bytes`, the size of `av1.mp4`) `/fail` (`error`, `retryable`) and `/release` (the lease alone), each with the lease; a report under a lease that is no longer current gets 409, and repeating a completion, failure or release is accepted. `release` is for a worker shutting down, never for a failure: the job goes back to `pending`, claimable at once, with its lease, `heartbeat_at` and `progress` cleared and the claim's attempt refunded (never below 0), and a `transcode`'s clip goes from `processing` back to `uploaded` in the same transaction. Only the first `Transcoding:MaxReleases` (default 10) releases of a job refund; later ones keep the attempt, so a worker restarted for ever runs the job out of attempts. The count and the released lease are kept in the run's `output` (`release_count`, `released_lease_id`; a completion keeps `release_count`). The endpoints use the `Worker` policy (a bearer matching `Worker:Secret`, the secret named `default`, or a named `Worker:Secrets:<name>` such as `gcp`, so each pool's credential is rotated or revoked on its own; each at least 32 characters, a shorter one ignored with a startup warning by `WorkerSecretsCheck`; compared in constant time against every secret without stopping at a match; none usable refuses everything; never the site cookie), which puts the matched secret's name on the principal (`WorkerAuthentication.WorkerName`) and in the claim, complete, fail and release log lines, the `worker` rate limit (`Worker:RequestsPerMinute`, per address) and are left out of the OpenAPI document, so the generated client doesn't change. Each claim first fails jobs out of attempts (`Transcoding:MaxAttempts`, default 3), then takes a pending job past its retry delay (`Transcoding:RetryAfter`) or a running one with no claim or progress for `Transcoding:StaleAfter` (default 5 minutes; workers report at least every 30 s for the whole job, so silence means the worker is gone), with `FOR UPDATE SKIP LOCKED`, so there is no background service. `Transcoding:WorkerJobTypes:<name>` (comma-separated, by the worker secret's name; none or empty means every type; an unknown type fails startup, and a name with no usable secret is a startup warning) limits what a pool's workers are handed, and its claims get 204 while only other types wait: prod keeps `audio` off the overflow pools, since a worker there pays for every byte it uploads and an `audio` job uploads a whole video for seconds of work; keep `Overflow:JobTypes` to the same types so the scaler doesn't start workers for jobs they can't take. `transcode`, `trim` and `audio` jobs change the clip, through `ClipVideoUpdateHandler` in the same transaction as the run: a transcode's progress sets `processing` and `encode_progress` (only from `uploaded` or `processing`); completion of any sets `ready` on the job's `video_version` with `length`, `storage_size` (the AV1 size; `file_size` is cleared, so the quota counts the output alone), `video_codecs` and `video_height` (codecs that aren't a plain RFC 6381 list are dropped), then deletes the uploaded source (a transcode) and the version the clip moved off (a trim or audio job) and queues a transcode's legend detection and transcription. Completion moves only a clip still on `r2` whose `video_version` isn't past the job's (`ClipsStatements.SetTranscodeReady`; nothing stops two trims on one clip); otherwise the job is superseded: it still succeeds, the clip, its source and its follow-ups are left alone, and the run's own `clips/{clipId}/v{n}/` is deleted unless the clip plays from that version, so trims finishing out of order never take a clip back; a final transcode failure sets `encode_failed` (only from `uploaded` or `processing`). Clips encoded before the move to AAC carry Opus audio: `AacBackfillService` (never in `OpenApi`, `Transcoding:AacBackfill`, off by default; turn it on only once every worker, overflow pools included, runs a build that knows `audio`) tops the queue up every `AacBackfillInterval` (1 min) to `AacBackfillBatchSize` (10) `audio` jobs at backfill priority 2, newest ready R2 clips whose `video_codecs` end `,opus` first, skipping clips with any job waiting or running and ones whose `audio` job already failed on that version (V66 adds the type and a partial unique index on a clip's active `audio` job). `Transcoding:QueueDetectionOnThumbnails` (default false) queues legend detection on the first `thumbnails_ready` report. The Bunny migration's `migrate` jobs (#239) moved every clip to R2; V62 deletes them and their type. See `reelshelf-docs/video-pipeline/workers-and-jobs.md`.
- The transcode worker (`workers/Reelshelf.Worker/`, #214) is a separate service that holds only `Worker__ApiBaseUrl` and `Worker__Secret` (no storage keys: it reads and writes through each job's presigned `source_url`/`upload_urls`). One job at a time: claim, stream the source to a per-job directory under `Worker:WorkDirectory` (deleted afterwards), ffprobe it (unreadable, no video or an empty trim fails with `retryable: false`), take the six frames (`thumbnail.jpg` at 0 like Bunny's `thumbnailTime` 0, `thumbnail_1..5.jpg` at 1/6 … 5/6, `FrameTimings`), full-range 4:2:0 JPEGs (`EncodeArguments.JpegFilter`; ffmpeg 7.1's mjpeg encoder refuses limited-range YUV), upload them and report `thumbnails_ready`, then encode with progress (every 5% or 10 s, heartbeat every `HeartbeatInterval`), upload and complete with `outputs.codecs` read back from the produced file (`Codecs`, e.g. `av01.0.08M.08,mp4a.40.2`), `width`, `height` and `files`. A `transcode` is SVT-AV1 (`Worker:Preset` 8, `LogicalProcessors` → `lp`, `TargetBitrateKbps` 4000 VBR, or `HighFrameRateBitrateKbps` 6000 above 32 fps) at the source's frame rate (`FrameRate.Target`: ffprobe's `avg_frame_rate`, else `r_frame_rate` when that is `0/0` or missing, kept as the exact rational such as `60000/1001`, capped at 60, and 30 when unknown or below 1) with `-fps_mode cfr` and `-g` the rate rounded (a keyframe a second, which stream-copied trims rely on), fitted in 1920×1080 (1080×1920 for portrait) without upscaling, even sides, 8-bit 4:2:0, AAC-LC stereo (`AudioBitrateKbps` 192; Safari, so every iPhone, plays no Opus in MP4), metadata stripped, `+faststart`, with the input's trim cut by input `-ss`/`-t` while re-encoding, plus a 3 s silent 640×360 15 fps AV1 `preview.mp4` when the job has a URL for it. HDR (PQ/HLG) is tone-mapped to BT.709 with zscale + Hable (`EncodeArguments.ToneMapFilter`; `outputs.tone_mapped`), and refused when ffmpeg lacks zscale. `trim` stream-copies the current output (`frame_accurate` re-encodes the range at its input's frame rate), re-encoding audio that isn't AAC, `audio` copies all of the current output's video and re-encodes its audio as AAC-LC into the next version (a whole copy keeps its timing; only a cut gets `-avoid_negative_ts make_zero`), and `thumbnails` only remakes the frames; `fallback` fails as unsupported. All ffmpeg runs go under `nice -n Worker:Niceness` (default 10). PUTs send exactly the signed `Content-Type` and `Cache-Control: public, max-age=31536000, immutable`. A 409 drops the job without a report; storage 5xx/network errors are retried, then fail as retryable; ffmpeg failures fail as retryable. It backs off while idle (`IdlePollInterval` 5 s doubling to `MaxIdlePollInterval` 60 s) and on API errors (`ErrorBackoff` 5 s to 5 min). With `Worker:ExitWhenIdleAfter` set (a TimeSpan, off by default, so the dedicated worker polls for ever; zero or negative fails startup) it exits with code 0 once it has gone that long without claiming a job, for the one-shot overflow workers (#246): any claim resets the clock, the last idle wait is cut short so the final empty claim lands at the limit, and time spent on failed claims and the error back-off doesn't count, so an API outage doesn't drain the pool. On SIGTERM a job whose encode (or trim) has started gets `ShutdownGrace` (20 s) and is then killed and released (`/release`, no attempt used); one that hasn't started encoding is released at once. Batch on GCE gives a preempted Spot VM's container no such grace, so with `Worker:PreemptionNotice=gce` (set by the overflow pool; empty by default) `GcePreemptionWatcher` holds a hanging GET on the metadata server's `instance/preempted` (`Worker:GceMetadataUrl`) and, when it turns `TRUE`, releases the job at once whatever its stage, claims nothing more, and waits for the VM to go rather than exiting, so Batch records exit code 50001 and retries the task. The container's stop timeout must exceed the grace plus ~15 s. Every real failure, an ffmpeg crash included and even during the grace, still goes through `/fail` and uses an attempt. Startup fails without libsvtav1/aac or with bad settings. Its integration tests (`[SvtAv1Fact]`) encode `lavfi` clips (a 60 fps one checked for 60 fps and keyframes a second apart) against a loopback fake API and storage (`FakeWorkerApi`) and skip when ffmpeg lacks libsvtav1; CI installs BtbN's static ffmpeg 8.1 build (SVT-AV1 4.x) from GitHub releases rather than Ubuntu's, whose mirror once stalled the job, and ffmpeg 8 ignores `-color_trc`/`-color_primaries` against the frames' own tags, so test sources are tagged with `setparams`. The image is `debian:trixie-slim` with the worker published self-contained (Microsoft's .NET 10 runtime images are Ubuntu 24.04), for Debian's ffmpeg 7.1 and SVT-AV1 2.3; its build fails on an SVT-AV1 older than 2.x, because 1.7 segfaulted inside `libSvtAv1Enc` on the dev server's VM (one CPU socket per vCPU) for ordinary clips; a crashed tool is reported by its signal (`FfmpegRunner.DescribeExit`).
- The overflow pool (`api/Video/Transcoding/Overflow/`, #248) starts one-shot transcode workers when `transcode_run` backs up, on the backends in `Overflow:Pools` (comma-separated, most preferred first, default `batch`; prod `ecs,batch`, to become `ec2,ecs,batch`): `ec2`, ECS tasks on AWS EC2 Spot instances, `ecs`, ECS tasks on AWS Fargate Spot (both `EcsOverflowTaskLauncher`, `AWSSDK.ECS`, one instance per pool with its own settings section, client and cluster), and `batch`, Google Cloud Batch (`BatchOverflowTaskLauncher`, `Google.Cloud.Batch.V1`), each behind `IOverflowTaskLauncher` (`OverflowPools` holds them in order). It first ran on AWS ECS alone (Fargate Spot, then EC2 Spot), which was removed on 2026-10-22 for Batch; Fargate Spot came back on 2026-11-03 as a second pool once Batch hit its CPU quota (plan in `reelshelf-docs/video-pipeline/fargate-overflow.md`), and EC2 Spot the same day as a third pool, first in the order, at about a third of Fargate's cost per clip (`reelshelf-docs/video-pipeline/ec2-overflow.md`). The workers exit once idle (`Worker__ExitWhenIdleAfter`), so the API never stops one. `OverflowBackgroundService` is registered only where `Overflow:Enabled` is true (default false), never in `OpenApi`, and each tick does nothing without R2. Every `Overflow:Interval` (30 s) `OverflowScaler` counts the claimable backlog by the claim's own rule (`pending`, `available_at <= now()`, `attempts < Transcoding:MaxAttempts`; `OverflowBacklogStatements`, over V40's `transcode_run_pending_idx`), optionally only `Overflow:JobTypes` (comma-separated; empty means every type, `migrate` included), ageing the oldest job from `available_at`, not `created_at`, so a released or retried job gives the dedicated worker the threshold first. It then counts each pool's workers running or provisioning (a pool whose count fails is taken as full: nothing starts there and it counts as its cap) and once the oldest job has waited `Overflow:ScaleUpAfter` (default 2 min; prod 30 s) starts `min(pending - running, MaxTasks - running, MaxStartPerTick)` (defaults 4 and 4) across the pools, and then none for `Overflow:Cooldown` (default 2 min; prod 0). They go to the pools in order, each up to its own cap (`Overflow:Ec2:MaxTasks`, `Overflow:Ecs:MaxTasks`, `Overflow:Batch:MaxTasks`, the backend's quota; 0 means `Overflow:MaxTasks`, which caps them together), and what a pool doesn't start (it threw, ECS reported no Spot capacity, or it is held back after a provisioning timeout) goes to the next in the same tick. Prod: Fargate 4 (the 8-vCPU Fargate Spot quota over 2-vCPU tasks), Batch 6 (the C4 quota in Paris), 10 in all. Each ECS scale-up is `RunTask` (10 per call) on the pool's `CapacityProvider` (`Overflow:Ecs:CapacityProvider` defaults to `FARGATE_SPOT`; `Overflow:Ec2:CapacityProvider`, the EC2 cluster's Auto Scaling group provider, has no default) in its `Cluster`, `startedBy` = `Overflow:StartedBy`, of its `TaskDefinition` family; only an `awsvpc` task definition (by the network mode of the revision described or registered, not a setting) gets a network configuration, `Subnets` with `SecurityGroups` and, on Fargate only, a public IP, while the EC2 pool's `host`-mode tasks use their instance's public IP and need neither setting. The family's size, network mode, roles, `Worker__Secret` (Secrets Manager, `Worker:Secrets:aws` on the API), environment and sandbox come from infrastructure's `aws/overflow-workers/` Terraform (applied from CI like `gcp/overflow-workers`); the API changes only the image: when the pool's `WorkerImage` is set and the latest revision runs another, it registers a copy with that image on each container of its repository (keeping placement constraints, leaving an EC2 revision's task-level size unset) and runs that (remembered per image with its network mode, found again after a failed `RunTask`). Fargate Spot's SIGTERM two minutes ahead, and on EC2 the agent's Spot draining (`ECS_ENABLE_SPOT_INSTANCE_DRAINING`), with `stopTimeout` 120 s let the worker release its job, so no preemption watcher. Counting is `ListTasks` in the pool's cluster by `startedBy`, desired `RUNNING` (which includes `PROVISIONING`, a task waiting for its instance) and `PENDING`; a task still `PROVISIONING` after the pool's `ProvisionTimeout` (`Overflow:Ec2:ProvisionTimeout`, `Overflow:Ecs:ProvisionTimeout`, 4 min) is stopped (`DescribeTasks`, `StopTask`) and left out, since managed scaling never refuses a task for want of capacity, and the pool then starts nothing for as long again, so the next pools take its share. Each client signs in with its pool's `AccessKeyId`/`SecretAccessKey` (both or neither) in its `Region`. Each Batch scale-up is one `CreateJob` of `count` tasks, one Spot VM each from `Overflow:Batch:InstanceTemplate` (which carries the machine, the network and a Standard-tier IP; Batch gives VMs from an instance policy a Premium-tier IP) with `Overflow:Batch:ServiceAccount`, running `Overflow:Batch:WorkerImage` with `Worker__ApiBaseUrl`, `Worker__LogicalProcessors` (`Vcpus`), `Worker__ExitWhenIdleAfter` (1 min), `Worker__PreemptionNotice=gce` and `Worker__Secret` from Secret Manager (`WorkerSecret`), retried on exit code 50001, labelled on the allocation policy `pool` = `Overflow:StartedBy`. Batch counting lists the pool's unfinished jobs (`allocation_policy.labels.pool=… AND status.state!=SUCCEEDED AND !=FAILED`) and adds each job's tasks less the succeeded and failed ones; a `QUEUED`/`SCHEDULED` job with no task ever started that is older than `Overflow:Batch:ProvisionTimeout` (3 min, short because its tasks hold places another pool could fill) is deleted instead, with Batch's last status event logged, and the pool then starts nothing for as long again. The Batch client signs in with `Overflow:Batch:CredentialsBase64` (the scaler service account's JSON key, base64) or Application Default Credentials. Startup fails when `Enabled` is on with no or unknown pools, and for each pool in use on its missing settings (Batch: `ProjectId`, `Region`, `InstanceTemplate`, `ServiceAccount`, `WorkerImage`, `WorkerSecret`, `ApiBaseUrl`; ECS pools: `Region`, `Cluster`, `CapacityProvider`, `TaskDefinition` (a family), for `ecs` `Subnets` and `SecurityGroups`, half a key, a `WorkerImage` without a tag, and both pools on one cluster), on a `StartedBy` that isn't a GCP label value, an unknown job type, or limits below 1. The bump PR rewrites `Overflow__Batch__WorkerImage=`, `Overflow__Ecs__WorkerImage=` and `Overflow__Ec2__WorkerImage=` with the worker's other tags. Each tick runs under a Postgres advisory lock (`PostgresOverflowTickLock`), so while a deploy runs two instances only one scales. Errors are logged and retried on the next tick. Metrics go on the `Reelshelf.Overflow` meter, exported with the queue gauges and tagged `pool`: the `reelshelf.overflow.tasks_running` gauge and the `tasks_started` counter. Plans in `reelshelf-docs/video-pipeline/batch-overflow.md`, `fargate-overflow.md` and `ec2-overflow.md`. Keep `Migration:BatchSize` above the total number of workers. See `reelshelf-docs/video-pipeline/workers-and-jobs.md`.

- Clip transcription (`api/ClipTranscription/`) sends a clip's audio, extracted with ffmpeg as mono 32 kbps AAC from the clip's MP4 (`ClipMediaUrls.ServerStream`), to OpenRouter's `audio/transcriptions` endpoint, where the model id picks the provider. The default is `google/gemini-3.5-transcribe` with the game name (and Apex legend names) as `custom_vocabulary`; when it hears nothing in a clip with audio, `ClipTranscription:FallbackModel` (default `deepgram/nova-3`) is tried before the clip is recorded as having no speech. Provider-specific settings go under `provider.options` in `OpenRouterClipTranscriber.ProviderOptions`. On a sample of clips, `gpt-transcribe` often returned nothing, `gpt-4o-transcribe` invented foreign words and `whisper-1` invents text for silence. It only covers clips whose owner's plan has transcripts (Pro or Unlimited, `TierLimits.HasTranscripts`), and transcripts are search data reviewed at `/clip-transcription`, never shown to owners. Runs are queued in `clip_transcription_run` and processed by a background service; nothing runs until `ClipTranscription:OpenRouterApiKey` is set, and `ClipTranscription:AutoQueue` queues a run when such an owner's clip finishes encoding. "Retry no-speech clips" on the review page re-runs clips whose latest empty result came from another model. Each instance processes `ClipTranscription:Concurrency` runs at once (default 2). An instance without the key never claims a run, and only prod has one, so dev never transcribes; it can still show the review page. See `reelshelf-docs/adr/0005-clip-transcription-and-search.md`.
- Clip summaries (`api/ClipSummary/`) turn a succeeded transcript, with the clip's game, title, date and, for Apex clips, the latest detected legend, into a description, mood tags (fixed list in `ClipMoodTags`), quotes and people, through a chat model set by `ClipSummary:Provider`, `Model` and `ReasoningEffort` with keys under `ClipSummary:Providers:<provider>:ApiKey`; new providers are a case in `ClipSummarizerFactory`. The prompt and schema are embedded from `Resources/` and hashed into the prompt version. Tags outside the list and quotes not found in the transcript are dropped. The description and tags are embedded with `ClipSummary:EmbeddingModel` (default `text-embedding-3-small`, always on the `openai` key) into a pgvector `vector(1536)` on the same `clip_summary_run` row, and a run succeeds only when both steps do. The migration needs the `vector` extension in Postgres; Npgsql is set up for it in `ReelshelfDataSource`. `ClipSummary:AutoQueue` queues a summary when an automatic transcription succeeds (and a `retry` summary when a transcription retry hears speech); an instance without the `openai` key never claims a run. Each instance processes `ClipSummary:Concurrency` runs at once (default 2). Summaries are reviewed, rerun and backfilled on `/clip-transcription`, never shown to owners. Tests marked `[PostgresFact]` need `REELSHELF_TEST_DATABASE` (CI runs a pgvector service) and are skipped without it.
- Clip search (`api/ClipSearch/`, ADR-0005) searches the caller's own clips by description: `POST /api/clips/search` (`clip-search` rate limit, `ClipSearch:RequestsPerMinute`, 20) takes `{ query, time_zone }`, and a chat model (`ClipSearch:Provider`, `Model`, `ReasoningEffort`, sent as Microsoft.Extensions.AI's reasoning option over Chat Completions; key under `ClipSearch:Providers:<provider>:ApiKey`, else the same provider's `ClipSummary` key; prompt and schema in `Resources/`) reads it, given today's date in that zone and the caller's games, into a date range, game ids (only their own), mood tags (`ClipMoodTags`), people and a leftover phrase. At most `ClipSearch:MaxResults` (50), in the library's `Clip` projection, with the `interpretation` it applied; sending that back as `filters` (some taken away) searches again without the model. It needs the `clip-search` flag (`RequireFeature`, 404 off), a plan with transcripts (403 otherwise) and a configured model and embedding key (503 otherwise); `GET /api/clips/search/availability` says which, and the library page offers "Describe a clip" (`ClipSearch.tsx`, `useClipSearchAvailable`) on `/` only when available, showing the interpretation as removable chips and keeping the search in sessionStorage. Summary text, quotes and people are never shown.
- Queue metrics (`api/QueueMetrics/`) report how each Postgres run queue is doing as observable gauges on the `Reelshelf.Queues` meter (`System.Diagnostics.Metrics`), tagged `queue` (`legend_detection`, `clip_transcription`, `clip_summary`, `transcode`) and `trigger` (for `transcode`, the job `type`): `reelshelf.queue.pending` (claimable now), `retrying` (pending, waiting out the retry delay), `oldest_pending_age` (seconds, 0 when empty), `running`, `stale_running` (past the queue's stale-after, so its worker died), and `succeeded_last_hour`, `failed_last_hour` and `exhausted_last_hour` (failed with at least the queue's `MaxAttempts`). Legend detection leaves out archived runs. `QueueMetricsBackgroundService` samples each table every `QueueMetrics:Interval` (default 30 s) with two grouped counts over the partial `*_queue_idx` and `*_finished_idx` (V41) indexes, and the gauges only read the latest sample; a queue whose sample fails stops reporting until the next one works. Retry and stale delays are the services' own `RetryAfter`/`StaleAfter`. `QueueMetrics:Enabled` (default true) turns the sampler off, and it never runs in the `OpenApi` environment. Every instance samples the same database, so with more than one instance read the numbers per instance, not summed. A new run table with the usual columns (`trigger`, `status`, `attempts`, `created_at`, `started_at`, `completed_at`) is one `AddRunTableQueueMetrics` line in `QueueMetricsSetup`; anything else implements `IRunQueueMetricsSource` and registers it in the same place, as `TranscodeRunMetricsSource` does for `transcode_run`: pending is `available_at <= now()` and retrying `available_at > now()`, stale running is a `heartbeat_at` older than `Transcoding:StaleAfter`, the hour is counted by `finished_at` (over `transcode_run_finished_idx`, V43, with V40's partial pending and running indexes for the rest), and exhausted also counts jobs with `Transcoding:MaxAttempts` used up that the next claim will fail (pending ones, which are left out of pending, retrying and the oldest age, and stale running ones), so it can exceed `failed_last_hour`. The overflow scaler (below) counts its own backlog instead of reading these gauges. Nothing is exported by default (`QueueMetrics:Exporter` `none`); read the gauges with `dotnet-counters monitor -p <pid> --counters Reelshelf.Queues`. `QueueMetrics:Exporter=otlp` pushes them through OpenTelemetry to `QueueMetrics:Otlp:Endpoint` (gRPC by default; `Otlp:Protocol=http/protobuf` takes the full `/v1/metrics` URL; `Otlp:Headers` for a hosted collector's auth; the `OTEL_EXPORTER_OTLP_*` variables apply when these are empty) every `Otlp:ExportInterval` (default 60 s), as service `reelshelf` with `deployment.environment.name`; an OpenTelemetry Collector or the CloudWatch agent can forward them to Prometheus/Grafana or CloudWatch. There is no scrape endpoint, so nothing new is public. The same exporter sends .NET's own meters too (`QueueMetricsSetup.PlatformMeters`: `Microsoft.AspNetCore.Hosting` for requests by route and status, `Microsoft.AspNetCore.Diagnostics`, `Microsoft.AspNetCore.RateLimiting`, `System.Net.Http` for calls to other services by host, `System.Runtime` and `Npgsql`), which need no instrumentation package; the API's Npgsql pools are named (`ReelshelfDataSource.PoolName`, and `HealthCheckPoolName` for the `/health` check's own pool) so their series never carry the connection string. Infrastructure's Grafana alerts on these (5xx share, latency) and on the queue gauges, posting to Discord.
- The Discord Activity (`api/Discord/DiscordActivity/`, frontend `components/Activity/`) is the watch room from ADR-0006. When the app is served from `*.discordsays.com`, `main.tsx` renders it instead of the router. `POST /api/activity/token` trades the Embedded App SDK's code for a short-lived room token, but only after Discord's activity-instances API confirms the user is in that instance, which needs `DiscordActivity:BotToken` (the Activity reports itself off until it is set). Room endpoints require the `Activity` policy (bearer room token), never the site cookie. Room token claims never use `NameIdentifier`, which the rest of the API reads as an account id. The room itself is a SignalR hub at `/api/activity/hub` (`WatchRoomHub`, camelCase JSON, hand-written client types in `shared/services/watchRoom.ts`). Rooms live in Redis (`RedisConnectionString`), so they outlive a deploy and any `clips` instance serves any room: each room is one JSON document (`WatchRoom`, its rules over `WatchRoomState`) under `reelshelf:<environment>:watch-rooms:v1:` (`RedisWatchRoomStore`; dev and prod may share a Redis), which `WatchRoomRegistry` loads, changes and saves only if it is unchanged since the read (a `WATCH` transaction), trying again from the newer room otherwise, so changes run more than once must stay pure. Hub broadcasts go through the SignalR Redis backplane (`AddStackExchangeRedis`, channels under the same prefix, not in `OpenApi`), so they reach connections on the old and new container while a deploy overlaps them. A dropped connection stays in the room for `WatchRoom.ReconnectGrace` (30 s), keeping the host role, its place for the next host and its owner's queued clips, and a person who rejoins in time picks up where they were; only when it is up do they leave (host passing on, a room with only guests emptying, a room with nobody closing). Each connection records its instance (`WatchRoomServer`), whose heartbeat (`server:<id>`, renewed every 10 s, lasting 30 s, written before the app listens and deleted on shutdown) lets other instances give a crashed instance's connections their grace. Reaction limits are per instance, in memory (`ReactionLimiter`). The first member to connect hosts. Any member can queue clips from their own shelf, in round-robin order by who queued them. Only the host plays, pauses, seeks or skips, and reorders, removes or locks the queue; the host's player reaching the end moves the room on (`Next` names the item it ends, so two of the host's devices move on once), and the room also keeps its own clock: `WatchRoomClock` (never in `OpenApi`; every instance runs it over every room, and the conditional save lets only one move a room on) moves a playing clip on `WatchRoom.EndGrace` (5 s) past its expected end (position plus the clip's `length` left), so a host whose stream failed doesn't stall the room; a paused clip, or one of unknown length, never moves on by itself, and a host whose browser refuses even muted autoplay reports a pause. Each change's broadcast state is the one its save stored (`WatchRoomRegistry.ApplyAsync`). A queued clip is shown only while its owner is in the room: an absent owner's clips are hidden and dropped when their turn comes. Queue items carry no video id until they play. Anyone in the room, guests included, can react to the playing clip with one of a fixed set of emoji (`WatchRoom.ReactionEmoji`, mirrored in `reactionEmoji`), limited per person; reactions go out once on `Reaction` and are never kept. Followers correct drift by nudging `playbackRate` and seek when more than a second out. The hub accepts the room token from the `access_token` query parameter (WebSockets can't send headers); nowhere else does. Room tokens are renewed through `POST /api/activity/token/refresh`, which checks the instance again; `useWatchRoom` holds the current one, and the clip picker reads it through `getRoomToken()` on each request rather than keeping the token the session began with. Members pick from their own clips (`GET /api/activity/clips`, newest or oldest first and optionally one game's, listed by day under a shelf of spines from `GET /api/activity/clips/games`, each game's cloth colour and clip count, loaded once so the spines keep their order) and the Activity plays the clip through the same `attachStream` as the rest of the site, in its own `ActivityPlayer` because the room drives it. Clips and the playing clip carry `media` (`ActivityMedia`: the host, the video's folder under its media origin from `ClipMediaUrls.MediaPath`, and the stream's type), from which `clipMediaUrls.ts` builds the path: R2's `av1.mp4` under `/media/clips/{clipId}/v{n}/`. The Discord application's URL Mappings need `/` → the prod site, `/discord-cdn` → `cdn.discordapp.com` and `/media` → the prod media domain (`R2:MediaBaseUrl`'s host). The Activity is built and tested on prod only.
- Content reports (`api/Moderation/`, V51 and V52; setup and runbook in `reelshelf-docs/moderation.md`): anyone watching a share link can report it (`POST /api/shared-clips/{token}/reports`, anonymous, `content-report` rate limit, `Moderation:ReportsPerMinute`, default 5) with a reason (`ContentReportReasons`), optional details and an optional email; the share page's `ReportClip` is the form. A report keeps the clip's title and owner after the clip is deleted (`content_report`). A `child_safety` or `terrorism` report (`ContentReportReasons.Urgent`) hides the share link at once while it is open (`ContentReportStatements.ShareableSql`, which `GetSharedClipByToken` uses, and which also hides every link of a suspended owner) and mails every Admin with an email. Admins review reports at `/admin/reports` (`/api/admin/reports`, `admin.reports`; `share_hidden` says a link is hidden, and child-safety reports never carry a `share_url`). Dismissing one leaves the clip alone. Other reports are taken down (a note is required): `clip.sharing_blocked_at` is set, its share links revoked and every open report on the clip but urgent ones resolved in one transaction, then the owner is mailed that it broke the terms, never which rule or who reported it, with `Moderation:ContactEmail` (default `support@reelshelf.app`) to dispute it; the clip stays in their library and `CreateOrGetShare` refuses it (403). Urgent reports can't be taken down, only removed (`POST .../remove`, `ContentReportStatements.Remove`): one transaction snapshots the clip row (`to_jsonb`, plus its game's name) and its owner with every linked sign-in into `clip_evidence`, suspends the owner (unless an Admin) through `AccountAccessStatements.SetSuspended`, resolves every open report on the clip as `removed` with its `evidence_id`, and deletes the clip row, so it vanishes everywhere at once; the owner isn't mailed, and removing needs `Moderation:EvidenceBucket` (409 without it). `ClipEvidenceProcessor` (`ClipEvidenceBackgroundService`, woken by `ClipEvidenceSignal`, never in `OpenApi`) then claims the record (attempts, stale claims, retries; every step write carries the claim's `claimed_at`, so a processor whose claim went stale writes nothing) and, recording each step so a retry resumes, never deletes the only copy (the law requires keeping it: OSA s66 and SI 2026/268 reg 8, EU TCO art. 6; "Legal basis" in `reelshelf-docs/moderation.md`): first it quarantines (`IEvidenceQuarantine`, `R2EvidenceQuarantine`): every object under `clips/{clipId}/` and `uploads/{clipId}` (its open upload aborted) is copied server side to `quarantine/{evidenceId}/{key}` in the media bucket (never overwriting a key already there) and the originals deleted, then the clip is purged from the media domain's CDN (`ICdnPurger`): on Cloudflare, versions 1 to `video_version + 1` by URL through its API (`Moderation:Cloudflare:ZoneId`/`ApiToken`), on CloudFront one invalidation of `/clips/{clipId}/*` and `/uploads/{clipId}*` (`Moderation:CloudFront:DistributionId`, `CloudFrontCdnPurger`, signed with the store's own AWS keys, which need `cloudfront:CreateInvalidation` on it; a fresh `CallerReference` each call, so the sweep invalidates again); setting both, or CloudFront with a `Storage:Endpoint` store, fails startup, and an accepted purge counts as done (`cdn_purge`, which marks the step done, records `not_configured` with neither and the admin page says to purge by hand), needing only the media bucket's credentials; then writes `{id}/record.json` and copies the video to `{id}/video.mp4` in the private evidence bucket (an `R2Storage` on that bucket with the `R2:*` credentials), the clip's `av1.mp4` from the quarantine (its uploaded source as `{id}/source` if it never encoded); only once `files` is set does it delete it at its host, every R2 version and the quarantine (`media_deleted_at`), making it `preserved`; and after `Moderation:SweepAfter` (3 h, above `Transcoding:PresignLifetime`) quarantines (deletes, once preserved) and purges `clips/{clipId}/` once more for late worker uploads. Preserving is never given up on: past `EvidenceMaxAttempts` the record is `failed` (needs attention, logged at Error, shown on the admin page) and retried with a back-off doubling up to `EvidenceMaxRetryAfter` (1 h). The media domain's WAF blocks `/quarantine/*` and the bucket's lifecycle rules leave it alone (`reelshelf-docs/video-pipeline/r2-bucket.md`). Evidence is deleted after `EvidenceRetention` (365 days), only once `preserved`. Suspension (`app_user.suspended_at`, recorded in `account_access_change` as field `suspended`) makes `AuthenticatedUserMiddleware` treat the account as signed out, refuses sign-in with `/sign-in?auth_error=suspended`, hides its share links and makes it a guest in the Activity; admins suspend and lift at `/admin/accounts` (`PUT /api/admin/accounts/{id}/suspension`), never themselves or an Admin. While an urgent report is open, `ClipService.DeleteClip` refuses the clip (409, a message that doesn't mention the report; the over-limit sweep skips it) and account deletion refuses its owner (`ContentReportStatements.IsHeldForReview`), so the evidence can't be destroyed before an admin decides; an account already being deleted waits instead (`IAccountDeletionStore.IsHeldForReview`, below). ## CI / Release

- `.github/workflows/ci.yml` runs on every PR and on pushes to `main`: `Frontend` (`bun run check`), `API` (`dotnet build` + `dotnet test` on `Reelshelf.sln`), and `API client drift` (`bun run check:api-client-drift`). All three must pass locally before opening a PR.
- `main` is protected by the "Protect main" repository ruleset: no direct pushes, force pushes, or deletions; changes land only via PRs with the three CI checks green. Repository admins can bypass only from the PR merge box, and GitHub records every bypass.
- Every PR body ends with a fenced `windlass` block declaring what the PR changes, for [Windlass](https://github.com/PlusCosmic/windlass) (`.github/workflows/windlass.yml`, policy `.windlass/policy.yaml`). It runs in shadow mode: it comments its verdict and labels the PR `windlass/would-merge`, `windlass/escalate` or `windlass/block`, and never merges. Declare `category: docs_only` when the PR changes only `README.md` files, `CONTEXT.md` or `docs/`; `category: test_only` when it changes only test sources (`tests/**/*.cs`, `desktop/*/tests/**/*.rs`, `frontend/src/**/*.test.ts(x)`, not project files or test config); otherwise the category that says what it is, such as `bugfix` (with `issue: <number>`), `feature`, `flagged_feature` (with `flag: <key>`) or `refactor`, which escalate to a human for now. The category is checked against the diff, never trusted, so declare what the PR actually is; a wrong one only escalates. Only `category`, `issue` and `flag` are read, and nothing else in the PR body reaches Windlass. Adding a test skip or a lint, type or coverage suppression (`it.skip`, `[Fact(Skip = …)]`, `#[ignore]`, `eslint-disable`, `#pragma warning disable`, …) blocks the PR. Changes to `.windlass/` always escalate.

  ````markdown
  ```windlass
  category: bugfix
  issue: 42
  ```
  ````

- `.github/workflows/publish-app-images.yml` builds GHCR images on `main` changes touching `api/`, `frontend/`, `migrations/`, `Dockerfile`, `package.json`, or `bun.lock`. Its `worker` job builds `ghcr.io/pluscosmic/reelshelf-worker:sha-<sha>` from `workers/Reelshelf.Worker/Dockerfile` (or on dispatch with `worker`); the image's build fails if its ffmpeg lacks libsvtav1, aac or zscale/tonemap.
- The workflow also opens an infrastructure PR bumping image tags in `PlusCosmic/infrastructure`, closing any older open bump PR. It decides what to build by diffing against the commits of the images currently deployed in that repo's `services/clips.yml`, not the previous push, so a superseded bump PR can't drop a migration; migration changes build the migrations image, and app-impacting changes build the app image. The worker follows the same model: it is built when `workers/` (or the workflow) changed since the `reelshelf-worker:sha-` commit deployed by any infrastructure `services/*.yml` with the worker's image (`reelshelf-worker-dev.yml`, and the prod file once it exists), and the same bump PR rewrites the worker tag in every such file, including `Overflow__Batch__WorkerImage=`, `Overflow__Ecs__WorkerImage=` and `Overflow__Ec2__WorkerImage=` in `services/clips.yml` (the overflow pools' image), which also counts as deploying it. A failed app build opens no bump PR, as before; a failed worker build only leaves the worker out of it. Runs are serialized.
