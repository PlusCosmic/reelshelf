# AGENTS.md

## Repo Shape

- `api/` is the .NET 10 ASP.NET API; real startup and endpoint wiring live in `api/Program.cs`.
- `frontend/` is the Bun workspace React 19/Vite/TanStack Router app; app entry is `frontend/src/main.tsx` and routes live under `frontend/src/routes/`.
- `migrations/` is a separate .NET 10 Evolve migration runner; the API does not run migrations on startup.
- `workers/Reelshelf.Worker/` is the transcode worker, a .NET 10 console app with its own `Dockerfile`; its tests are `tests/Reelshelf.Worker.Test/`.
- `frontend/src/api-client/` and `frontend/src/routeTree.gen.ts` are generated and committed; do not hand-edit them.

## Commands

- Install with `bun install` from the repo root; this repo pins `bun@1.3.13` in `package.json`.
- Root verification: `bun run check` runs `build -> typecheck -> lint -> test -> format:check`.
- Focused frontend checks: `bun run build`, `bun run typecheck`, `bun run lint`, `bun run test` from root delegate into `frontend/`.
- API build: `bun run build:api` or `dotnet build Reelshelf.sln --disable-build-servers -maxcpucount:1`.
- Prefer the existing dev runner in `~/dev/infrastructure/services/clips-dev.yml` for live development instead of manually running the frontend and API.
- The frontend test script is Vitest with `--passWithNoTests`; it runs every `*.test.ts(x)` under `frontend/src/` (e.g. `utils/s3MultipartUpload.test.ts`).

## Generated Code

- After API contract changes, run `bun run generate:api-client`; it builds the API with `ASPNETCORE_ENVIRONMENT=OpenApi` and regenerates `frontend/src/api-client/`.
- Check committed client drift with `bun run check:api-client-drift`.
- TanStack Router generates `frontend/src/routeTree.gen.ts` from files in `frontend/src/routes/`; edit route files, not the generated tree.

## Local Dev Quirks

- `clips-dev` bind-mounts this repo, runs `dotnet watch` plus the Vite frontend, exposes Vite on `5173`, and routes `/api` and `/auth` to the local API process.
- The dev runner passes `--host 0.0.0.0` to Vite; do not reintroduce a hard-coded local dev hostname in `frontend/vite.config.ts`.
- Frontend API clients default to same-origin requests; set `VITE_API_BASE_URL` only for split frontend/backend deployments.
- `clips-dev` has its own database, a one-off copy of prod with its own Bunny videos and `Development-` collections (`scripts/dev-db/README.md`), and migrates it to the checkout's migrations when it starts. A migration edited after dev applied it fails Evolve's checksum check there; fix the dev database rather than the check.
- API config uses `DatabaseConnectionString` or `ConnectionStrings__DatabaseConnectionString`; Redis defaults to `localhost:6379` if unset.

## Migrations

- Run migrations explicitly with `DatabaseConnectionString="Host=...;Database=...;Username=...;Password=..." bun run migrate`.
- First-time adoption for an existing production database is `bun run migrate:adopt-existing`; it records baseline `V16` without executing the baseline SQL.
- Normal migration runs refuse a non-empty database with no Evolve `changelog`; do not bypass this safety in code changes.
- New SQL migrations belong in `migrations/db/migrations/` using Evolve names such as `V17__game_category_igdb_assets.sql`.

## API Conventions

- JSON is configured as `snake_case` in `api/Program.cs`; generated TypeScript clients reflect that contract.
- Auth endpoints are intentionally at root `/auth` for OAuth callback compatibility; other API endpoints are grouped under `/api`.
- `api/whitelist.json` does not gate access. Any Discord or Twitch account can sign in; entries match a linked identity by `DiscordId` or `TwitchId`, and listed users get unlimited clip storage and may pin a role. Everyone else gets the default tier from `Storage:DefaultLimitBytes` (25 GiB). See `docs/adr/0002-open-signup-with-storage-tiers.md`.
- Sign-in providers are Discord and Twitch (`DiscordClientId`/`DiscordClientSecret`, `TwitchClientId`/`TwitchClientSecret`). Accounts live in `app_user`; each provider login is a `user_identity` row, and one account may link both. All four credentials are required: the API throws on startup when any is missing or blank, so a misconfigured deployment fails immediately instead of returning a 500 from `/auth/{provider}/login`. The `OpenApi` environment is exempt because document generation builds the app without secrets. IGDB game search uses the same Twitch application's credentials (IGDB has none of its own), so there are no separate IGDB settings. See `docs/adr/0003-linked-identities.md`.
- Twitch clip import (`api/Twitch/`) lists and copies a user's own Twitch clips server-side. It needs the `channel:manage:clips` scope, which is in the default `Twitch:Scopes`; Twitch tokens are stored encrypted on `user_identity` and refreshed on demand. See `docs/adr/0004-twitch-clip-import.md`.
- Account mail (linked sign-in notices, storage nearly full) goes through Resend via `ResendApiKey` and `Email__From`; with no key the API logs what it would have sent. See `api/Email/`.
- Apex legend detection (`api/ApexLegends/LegendDetection/`) sends the embedded prompt, schema and reference sheet in `Resources/` to a vision model via Microsoft.Extensions.AI, with each of the clip's six Bunny thumbnails as a half-resolution overview plus an enlarged close-up of the bottom-left HUD panel, both made with ffmpeg (`LegendHudCropper`; CI installs ffmpeg for its tests). Runs are queued in `legend_detection_run` and processed by a background service; nothing runs until `LegendDetection:Model` and `LegendDetection:Providers:<provider>:ApiKey` are set, and `LegendDetection:AutoDetect` queues a run when an Apex clip finishes encoding. Each run records its reasoning effort (`LegendDetection:ReasoningEffort` by default, or chosen on `/legend-detection`), and each API instance processes `LegendDetection:Concurrency` runs at once (default 4; dev and prod each have their own queue but share the provider's rate limit). `LegendDetection:EscalationModel` (off when empty) queues an `escalation` run with a stronger model on the same provider when an automatic run sees the owner's HUD but returns no legend or one below `EscalateBelow` (default 0.9); manual and escalation runs are claimed before automatic ones. Each instance escalates by its own config, so set it on dev and prod alike; `LegendDetection:EscalationProvider` escalates to another provider (empty keeps the run's own). New providers are a case in `LegendRecognizerFactory`. The `openai-decisions` provider is OpenAI's Decisions API (`DecisionsLegendRecognizer`, plain HTTP since the .NET SDK lacks it, in public beta): it reuses the `openai` key, defaults to `gpt-6-luna`, takes no reasoning effort, sends `Resources/decisions-prompt.md` with the same images, and asks a `hud_detected` predicate and a `legend` choice over `ApexLegendNames` plus `unidentifiable`; the legend's confidence is the probability the API gives the chosen option. Its prompt version is hashed separately (`DecisionsPromptVersion`). The `openrouter-decisions` provider (`OpenRouterDecisionsLegendRecognizer`) asks the same two questions of a decisions model on OpenRouter's Decisions API (`/api/alpha/decisions`), with the `openrouter` key and `typesafe/jev-1.14` (TypeSafe's Jev) by default; Jev takes images of 256 to 1,568 pixels a side (and at least 78,400 pixels), so it gets the reference sheet in halves (`LegendDetectionResources.ReferenceSheetHalvesAsync`, ffmpeg) and every screenshot fitted to those bounds (`LegendHudCropper.FitAsync`), since the close-up of a 1440p or 4K frame is too wide and that of a low-resolution frame too short. The `anthropic` provider (`AnthropicLegendRecognizer`, official `Anthropic` SDK) sends the chat prompt and schema to Claude (e.g. `claude-sonnet-5-5`, `claude-haiku-5-5`) with the halved sheet, a cache breakpoint after it, and the effort as `output_config.effort` (`none`/`minimal` fail the run); it asks for no refusal fallback, so a run's answer always comes from the model it names. Each has its own prompt version. `/legend-detection/evals` compares models: an eval (`legend_eval`) queues one `eval`-trigger run of a provider, model and effort on every labelled clip. Eval runs are claimed after every other run, are never archived by "Start fresh", and are left out of a clip's current legend (the review list, the baseline and clip summaries), so they never change what Reelshelf shows. Evals are scored against the labels as they are when read (failed runs count as wrong) and costed from the provider's billed cost (`cost_usd`, which OpenRouter reports) or from `legend_model_price`, prices per million tokens set on the page, so fixing a label or a price re-scores or re-costs every eval. Latency is the model call alone. The page's cascade panel works out production's escalation from two finished evals (`GET /api/legend-detection/evals/cascade`): the first eval's answer, or the second's where production would escalate (succeeded, HUD seen, no legend or one below the threshold), with accuracy, cost and mean time at each threshold, without running anything again. `/legend-detection/baseline` labels every Apex clip's owner's legend quickly: clips are grouped by their answer (the label, else the latest succeeded run), shown as HUD close-ups cut from the Bunny thumbnails with CSS and with portraits cut from the reference sheet (`GET /api/legend-detection/reference-sheet`, so its legends must stay in `ApexLegendNames` order, half on each of two rows); fixing a clip saves its label at once and confirming a group saves the rest through `PUT /api/legend-detection/labels`.
- Clip videos go through `IClipVideoHost` (`api/Video/`): create (filed in a per-owner, per-category container), server-side upload, fetch, delete. Each clip records the host holding its video in `clip.video_host` (`bunny` or `r2`, `VideoHostNames`, check constraint from V39), and every per-clip call goes to that host through `ClipVideoHosts`; hosts are keyed services registered by name with `AddClipVideoHost<THost, TMediaUrls>` in `ReelshelfApiConfiguration`, which is all adding one takes (plus its name in the constraint). New uploads follow `NewUploadVideoHostPolicy`: `VideoHost:NewUploads` (default `bunny`) is used only for the account ids in `VideoHost:Users`; everyone else, and everyone when the list is empty, stays on Bunny, and existing clips never move. Startup fails when `NewUploads` names a host that isn't registered. `BunnyService` is the only code that talks to Bunny's API; its collections (`clip_collection`) are its containers, and account deletion deletes containers at their own host (a host without containers has none). `CreateVideoAsync` gets the reserved clip's id. The `r2` host (`api/Video/R2/`, #212) is our own pipeline: Cloudflare R2 through AWSSDK.S3 with S3-compatible calls only (`R2Storage`), registered by `AddR2VideoHost` only when all of `R2:AccountId`, `R2:AccessKeyId`, `R2:SecretAccessKey`, `R2:Bucket` and `R2:MediaBaseUrl` (the media domain's https origin, never `r2.dev`) are set; a partial `R2` section fails startup, and so does `VideoHost:NewUploads=r2` without it. Dev and prod have separate buckets. An R2 clip's video id is its clip id; the source goes to `uploads/{clipId}` and outputs to `clips/{clipId}/v{n}/` (`av1.mp4`, `thumbnail.jpg`, `thumbnail_1..5.jpg`, `preview.mp4`; `R2ObjectKeys`), with the clip's current version, codecs and height in `clip.video_version`, `video_codecs` and `video_height` (V42). R2 has no video object or container: `GetVideoAsync` answers from the clip row, `NeedsStatusPolling` is false so `ClipStatusRefreshService` and the metadata backfill skip R2 clips, delete removes `uploads/{clipId}` and `clips/{clipId}/`, and `DeleteContainerAsync` does nothing. `UploadAsync` (Twitch import) streams to `uploads/{clipId}` (one PUT, or 8 MiB multipart parts, aborted on failure) and then marks the clip `uploaded` and enqueues its `transcode` in one transaction. Browser uploads to R2 (#213) are presigned S3 multipart uploads: `CreateUploadTargetAsync` (which gets the reserved file size) starts one on `uploads/{clipId}` and returns protocol `s3-multipart`, the endpoint `/api/clips/videos/{clipId}/upload` and `multipart` (`upload_id`, `part_size`, `part_count`; `MultipartUploadParts`: 8 MiB parts, larger in whole MiB when a file would need more than 10,000, so any declarable size fits). R2's `R2VideoHost` implements `IMultipartUploadHost`, and `MultipartUploadEndpoints` (owner-only, each with `RequireAuthorization()` and `clips.create`; any other caller or host gets 404) offers `POST .../upload/parts` (up to 100 part URLs per call, part numbers 1 to `part_count`, each a 1-hour presigned PUT signing only the host), `GET .../upload/parts?uploadId=` (the parts R2 holds, for resuming) and `POST .../upload/complete` (every part with its ETag; rate-limited with clip preparation). Completing joins the parts, requires the object to be exactly the reserved `file_size` (so the quota holds), and runs a cheap ffprobe (`FfprobeUploadProbe`, 30 s timeout) over a 10-minute presigned GET: no video stream, no picture size, no duration or an unreadable file marks the clip `upload_failed`, deletes the object and answers 422 with the reason; a probe that times out or can't read from storage answers 503 and leaves the clip waiting, and completing again picks up the joined object. HDR and variable frame rate are left to the worker. A passing file goes through the same mark-`uploaded`-and-enqueue transaction as `UploadAsync`, and repeating a completion is accepted. Storage quota and the MD5 duplicate check (403/409) stay at preparation in `ClipService.CreateClip`, the same for both hosts. No upload id is stored: deleting an R2 clip (the uploader's cancel, the abandoned-upload purge, account deletion) first aborts any open multipart upload on its key (`ListMultipartUploads` by prefix), and the bucket's lifecycle rule aborts what is left after a day. The browser side is `frontend/src/utils/s3MultipartUpload.ts` (hand-written, no Uppy): 4 parts at once, URLs asked for 10 at a time, each part retried with backoff, progress per finished part, and the clip, upload id and finished parts' ETags kept in localStorage under the book, MD5 and size, so dropping the same file on the same book after a reload resumes it (reconciled with the part list; a gone upload's clip is deleted and the file prepared afresh). `clipUpload.ts` picks tus or S3 by the target's protocol. Downloads (`GET /api/ffmpeg/download/{videoId}`, `api/FFmpeg/`, after the usual owner-or-`UserCanAccessClip` check, 404 otherwise) depend on the host: a host that registers a keyed `IClipVideoDownloads` (R2's `R2Downloads`; `ClipVideoHosts.DownloadsFor`) answers with a `no-store` 302 to a 10-minute presigned GET of the current `clips/{clipId}/v{n}/av1.mp4` carrying `response-content-disposition: attachment; filename="<title>.mp4"; filename*=UTF-8''<title>.mp4` (the title cleaned by `DownloadFileName`, the quoted name ASCII-only), and only for `ready` clips (404 before); Bunny clips are still remuxed from HLS by `FFmpegService`. The download button is a plain link, never fetch, so the browser follows the redirect without CORS on the bucket. Bucket lifecycle rules, CORS, caching and the presigned URL contract are in `docs/video-pipeline/r2-bucket.md`. Outside `api/Bunny/`, nothing names a Bunny model: the `Clip` contract's `video` is the app's own `ClipVideo` (`api/Core/Models/Clip.cs`), and `BunnyVideo` is only Bunny's API model. Every media URL (thumbnail, playback sources, the server-side stream ffmpeg reads, detection frames) is built by `ClipMediaUrls` (`api/Core/`) from the clip's `ClipVideoRef` (`video_host`, `video_id`, `video_version`, `video_codecs`, `video_height`, `video_state`, plus `thumbnails_ready` from `ClipVideoColumns.ThumbnailsReadySql`; rows that show media implement `IClipVideoColumns` and select all seven, and a row missing `video_state` reads as `awaiting_upload`, so it hands out nothing) and that host's `IClipVideoMediaUrls` (`BunnyMediaUrls`, or `R2MediaUrls` on `R2:MediaBaseUrl`), and handed out on the responses that show a clip (`ClipVideo`, shared clips, collection previews, legend detection and transcription review); the frontend builds none, except the Discord Activity's paths in `frontend/src/shared/utils/clipMediaUrls.ts` (`/bunny-cdn` for Bunny, `/media` for R2), which must go through Discord's URL Mappings. Nothing hands out a URL before its file exists (#229), since the browser never retries a failed `<img>` and Cloudflare caches R2's header-less 404 for its default 3 minutes: `sources` are `[]` until the clip is `ready`, at both hosts, and an R2 clip's thumbnail (`thumbnail_url`, null until then) and detection frames (`[]`) wait until it is `ready` or a worker has reported `thumbnails_ready` for its current `video_version` (`transcode_run.thumbnails_ready_at`). Bunny's thumbnails are handed out from the start, as before. The Activity's `ActivityMedia` carries `type` (null until ready) and `has_thumbnail` for the same reason. Players get a clip's `sources` (`PlaybackSource`: `url`, full MIME `type` with codecs, optional `height`), in the order to try them; a Bunny video is one HLS source (`application/vnd.apple.mpegurl`), and an R2 video is one progressive AV1 MP4 (`video/mp4; codecs="..."` from the worker's reported codecs, plain `video/mp4` without them, with its height). Every player on the site (clip page, share page, legend and transcription review) is `components/Video/ClipVideoPlayer.tsx`, rendered through `ClipVideoStage` (same folder), which shows the clip's processing state instead until `video.status` is `ready`: the thumbnail once it exists (the game's cloth before), "Processing" with the encode percentage, or a message for `encode_failed` and `upload_failed` (`awaiting_upload` and `uploaded` count as processing). The legend and transcription review clips carry `video_status` for it; the share page only ever gets ready clips. An open clip that is still processing is refetched every 3 s (`useClip`), the library's pages every 5 s, and clip cards render no `<img>` until there is a thumbnail. The player itself is a native `<video controls>` fed by `attachStream` (`shared/utils/videoStream.ts`, which the Activity shares), which attaches the first source the device can play. An MP4 is checked with `navigator.mediaCapabilities.decodingInfo` (else `canPlayType`) and played as the video's own `src`; HLS goes to hls.js (light build, loaded lazily) wherever MediaSource exists and plays natively where it doesn't (iPhone Safari). When no source can play, the player says "This clip can't play on this device", which means a `ready` clip this device can't decode and is where a fallback would plug in. There is no embed player or iframe. A clip's status is the app's own `ClipVideoStatus` (`api/Video/ClipVideoStatus.cs`), stored as text in `clip.video_state` (`awaiting_upload`, `uploaded`, `processing`, `ready`, `encode_failed`, `upload_failed`, the same spelling as `video.status` on the `Clip` contract); the host maps its statuses onto it (`BunnyService.ToClipVideoStatus`). Only `ready` is playable. The legacy `clip.video_status` column still gets Bunny's raw number (`HostedVideoInfo.HostStatus`) so the previous image works during a deploy; nothing reads it, and a later migration drops it. Bunny's webhook checks its secret and hands the video id to `ClipVideoUpdateHandler`, which re-reads the video, updates the clip and queues legend detection and transcription once it is encoded; `ClipStatusRefreshService` polls unfinished clips through the host and purges abandoned uploads.
- Transcoding (`api/Video/Transcoding/`, #208) is the queue for our own R2 + AV1 pipeline; the R2 host enqueues a `transcode` when an upload completes. Jobs are rows in `transcode_run` (type `transcode`, `thumbnails`, `trim` or `fallback`; `pending` → `running` → `succeeded`/`failed`; `input`/`output` jsonb, `video_version`, `priority`), queued with `TranscodeQueue.EnqueueAsync`, and a clip has at most one pending or running `transcode`. Workers are a separate service and never touch Postgres: they call `POST /api/worker/claim` (204 when idle; else the job, a `lease_id`, a presigned GET `source_url` for its input and presigned PUT `upload_urls` by output file name, which sign `Content-Type` and `Cache-Control: public, max-age=31536000, immutable` and live `Transcoding:StaleAfter` plus an hour; both null while R2 isn't configured, through `ITranscodeStorage`), then `/api/worker/{runId}/progress` (`percent`, `thumbnails_ready`), `/complete` (`outputs`: `codecs`, `width`, `height`, `files`; `length_seconds`; `size_bytes`, the size of `av1.mp4`) `/fail` (`error`, `retryable`) and `/release` (the lease alone), each with the lease; a report under a lease that is no longer current gets 409, and repeating a completion, failure or release is accepted. `release` is for a worker shutting down, never for a failure: the job goes back to `pending`, claimable at once, with its lease, `heartbeat_at` and `progress` cleared and the claim's attempt refunded (never below 0), and a `transcode`'s clip goes from `processing` back to `uploaded` in the same transaction. Only the first `Transcoding:MaxReleases` (default 10) releases of a job refund; later ones keep the attempt, so a worker restarted for ever runs the job out of attempts. The count and the released lease are kept in the run's `output` (`release_count`, `released_lease_id`; a completion keeps `release_count`). The endpoints use the `Worker` policy (the `Worker:Secret` bearer, at least 32 characters, compared in constant time; unset refuses everything; never the site cookie), the `worker` rate limit (`Worker:RequestsPerMinute`, per address) and are left out of the OpenAPI document, so the generated client doesn't change. Each claim first fails jobs out of attempts (`Transcoding:MaxAttempts`, default 3), then takes a pending job past its retry delay (`Transcoding:RetryAfter`) or a running one with no claim or progress for `Transcoding:StaleAfter` (default 1 hour), with `FOR UPDATE SKIP LOCKED`, so there is no background service. `transcode` and `trim` jobs change the clip, through `ClipVideoUpdateHandler` in the same transaction as the run: a transcode's progress sets `processing` and `encode_progress`; completion of either sets `ready` on the job's `video_version` with `length`, `storage_size` (the AV1 size; `file_size` is cleared, so the quota counts the output alone), `video_codecs` and `video_height` (codecs that aren't a plain RFC 6381 list are dropped), then deletes the uploaded source (a transcode) and the version the clip moved off (a trim) and queues a transcode's legend detection and transcription as the webhook does; a final transcode failure sets `encode_failed` (a clip already `ready` stays so). The legacy `video_status` column is never written for these clips and stays NULL. `Transcoding:QueueDetectionOnThumbnails` (default false) queues legend detection on the first `thumbnails_ready` report. See `docs/video-pipeline/workers-and-jobs.md`.
- The transcode worker (`workers/Reelshelf.Worker/`, #214) is a separate service that holds only `Worker__ApiBaseUrl` and `Worker__Secret` (no storage keys: it reads and writes through each job's presigned `source_url`/`upload_urls`). One job at a time: claim, stream the source to a per-job directory under `Worker:WorkDirectory` (deleted afterwards), ffprobe it (unreadable, no video or an empty trim fails with `retryable: false`), take the six frames (`thumbnail.jpg` at 0 like Bunny's `thumbnailTime` 0, `thumbnail_1..5.jpg` at 1/6 … 5/6, `FrameTimings`), upload them and report `thumbnails_ready`, then encode with progress (every 5% or 10 s, heartbeat every `HeartbeatInterval`), upload and complete with `outputs.codecs` read back from the produced file (`Codecs`, e.g. `av01.0.08M.08,opus`), `width`, `height` and `files`. A `transcode` is SVT-AV1 (`Worker:Preset` 8, `LogicalProcessors` → `lp`, `TargetBitrateKbps` 4000 VBR), `fps=30 -fps_mode cfr`, `-g 30`, fitted in 1920×1080 (1080×1920 for portrait) without upscaling, even sides, 8-bit 4:2:0, Opus stereo (`AudioBitrateKbps` 128), metadata stripped, `+faststart`, with the input's trim cut by input `-ss`/`-t` while re-encoding, plus a 3 s silent 640×360 15 fps AV1 `preview.mp4` when the job has a URL for it. HDR (PQ/HLG) is tone-mapped to BT.709 with zscale + Hable (`EncodeArguments.ToneMapFilter`; `outputs.tone_mapped`), and refused when ffmpeg lacks zscale. `trim` stream-copies the current output (`frame_accurate` re-encodes the range) and `thumbnails` only remakes the frames; `fallback` fails as unsupported. All ffmpeg runs go under `nice -n Worker:Niceness` (default 10). PUTs send exactly the signed `Content-Type` and `Cache-Control: public, max-age=31536000, immutable`. A 409 drops the job without a report; storage 5xx/network errors are retried, then fail as retryable; ffmpeg failures fail as retryable. It backs off while idle (`IdlePollInterval` 5 s doubling to `MaxIdlePollInterval` 60 s) and on API errors (`ErrorBackoff` 5 s to 5 min). On SIGTERM a job whose encode (or trim) has started gets `ShutdownGrace` (20 s) and is then killed and released (`/release`, no attempt used); one that hasn't started encoding is released at once. The container's stop timeout must exceed the grace plus ~15 s. Every real failure, an ffmpeg crash included and even during the grace, still goes through `/fail` and uses an attempt. Startup fails without libsvtav1/libopus or with bad settings. Its integration tests (`[SvtAv1Fact]`) encode `lavfi` clips against a loopback fake API and storage (`FakeWorkerApi`) and skip when ffmpeg lacks libsvtav1; CI's Ubuntu ffmpeg (SVT-AV1 1.7) has it. The image is `debian:trixie-slim` with the worker published self-contained (Microsoft's .NET 10 runtime images are Ubuntu 24.04), for Debian's ffmpeg 7.1 and SVT-AV1 2.3; its build fails on an SVT-AV1 older than 2.x, because 1.7 segfaulted inside `libSvtAv1Enc` on the dev server's VM (one CPU socket per vCPU) for ordinary clips; a crashed tool is reported by its signal (`FfmpegRunner.DescribeExit`).
- Game categories carry a `cloth_color` (#rrggbb) for their book on the library shelf, taken from the IGDB cover by `ClothColor` (ffmpeg downsample, dominant hue, muted). It is worked out when a game is added and backfilled by `GameCategoryClothColorService`; only `https://images.igdb.com` covers are fetched, so custom categories stay null and the frontend falls back.
- Clip transcription (`api/ClipTranscription/`) sends a clip's audio, extracted with ffmpeg as mono 32 kbps AAC from the Bunny HLS stream, to OpenRouter's `audio/transcriptions` endpoint, where the model id picks the provider. The default is `google/gemini-3.5-transcribe` with the game name (and Apex legend names) as `custom_vocabulary`; when it hears nothing in a clip with audio, `ClipTranscription:FallbackModel` (default `deepgram/nova-3`) is tried before the clip is recorded as having no speech. Provider-specific settings go under `provider.options` in `OpenRouterClipTranscriber.ProviderOptions`. On a sample of clips, `gpt-transcribe` often returned nothing, `gpt-4o-transcribe` invented foreign words and `whisper-1` invents text for silence. It only covers clips whose owner is whitelisted, and transcripts are search data reviewed at `/clip-transcription`, never shown to owners. Runs are queued in `clip_transcription_run` and processed by a background service; nothing runs until `ClipTranscription:OpenRouterApiKey` is set, and `ClipTranscription:AutoQueue` queues a run when a whitelisted owner's clip finishes encoding. "Retry no-speech clips" on the review page re-runs clips whose latest empty result came from another model. Each instance processes `ClipTranscription:Concurrency` runs at once (default 2). An instance without the key never claims a run, and only prod has one, so dev never transcribes; it can still show the review page. See `docs/adr/0005-clip-transcription-and-search.md`.
- Clip summaries (`api/ClipSummary/`) turn a succeeded transcript, with the clip's game, title, date and, for Apex clips, the latest detected legend, into a description, mood tags (fixed list in `ClipMoodTags`), quotes and people, through a chat model set by `ClipSummary:Provider`, `Model` and `ReasoningEffort` with keys under `ClipSummary:Providers:<provider>:ApiKey`; new providers are a case in `ClipSummarizerFactory`. The prompt and schema are embedded from `Resources/` and hashed into the prompt version. Tags outside the list and quotes not found in the transcript are dropped. The description and tags are embedded with `ClipSummary:EmbeddingModel` (default `text-embedding-3-small`, always on the `openai` key) into a pgvector `vector(1536)` on the same `clip_summary_run` row, and a run succeeds only when both steps do. The migration needs the `vector` extension in Postgres; Npgsql is set up for it in `ReelshelfDataSource`. `ClipSummary:AutoQueue` queues a summary when an automatic transcription succeeds (and a `retry` summary when a transcription retry hears speech); an instance without the `openai` key never claims a run. Each instance processes `ClipSummary:Concurrency` runs at once (default 2). Summaries are reviewed, rerun and backfilled on `/clip-transcription`, never shown to owners. Tests marked `[PostgresFact]` need `REELSHELF_TEST_DATABASE` (CI runs a pgvector service) and are skipped without it.
- Queue metrics (`api/QueueMetrics/`) report how each Postgres run queue is doing as observable gauges on the `Reelshelf.Queues` meter (`System.Diagnostics.Metrics`), tagged `queue` (`legend_detection`, `clip_transcription`, `clip_summary`, `transcode`) and `trigger` (for `transcode`, the job `type`): `reelshelf.queue.pending` (claimable now), `retrying` (pending, waiting out the retry delay), `oldest_pending_age` (seconds, 0 when empty), `running`, `stale_running` (past the queue's stale-after, so its worker died), and `succeeded_last_hour`, `failed_last_hour` and `exhausted_last_hour` (failed with at least the queue's `MaxAttempts`). Legend detection leaves out archived runs. `QueueMetricsBackgroundService` samples each table every `QueueMetrics:Interval` (default 30 s) with two grouped counts over the partial `*_queue_idx` and `*_finished_idx` (V41) indexes, and the gauges only read the latest sample; a queue whose sample fails stops reporting until the next one works. Retry and stale delays are the services' own `RetryAfter`/`StaleAfter`. `QueueMetrics:Enabled` (default true) turns the sampler off, and it never runs in the `OpenApi` environment. Every instance samples the same database, so with more than one instance read the numbers per instance, not summed. A new run table with the usual columns (`trigger`, `status`, `attempts`, `created_at`, `started_at`, `completed_at`) is one `AddRunTableQueueMetrics` line in `QueueMetricsSetup`; anything else implements `IRunQueueMetricsSource` and registers it in the same place, as `TranscodeRunMetricsSource` does for `transcode_run`: pending is `available_at <= now()` and retrying `available_at > now()`, stale running is a `heartbeat_at` older than `Transcoding:StaleAfter`, the hour is counted by `finished_at` (over `transcode_run_finished_idx`, V43, with V40's partial pending and running indexes for the rest), and exhausted also counts jobs with `Transcoding:MaxAttempts` used up that the next claim will fail (pending ones, which are left out of pending, retrying and the oldest age, and stale running ones), so it can exceed `failed_last_hour`. Its `oldest_pending_age` is the signal for scaling overflow workers. Nothing is exported by default (`QueueMetrics:Exporter` `none`); read the gauges with `dotnet-counters monitor -p <pid> --counters Reelshelf.Queues`. `QueueMetrics:Exporter=otlp` pushes them through OpenTelemetry to `QueueMetrics:Otlp:Endpoint` (gRPC by default; `Otlp:Protocol=http/protobuf` takes the full `/v1/metrics` URL; `Otlp:Headers` for a hosted collector's auth; the `OTEL_EXPORTER_OTLP_*` variables apply when these are empty) every `Otlp:ExportInterval` (default 60 s), as service `reelshelf` with `deployment.environment.name`; an OpenTelemetry Collector or the CloudWatch agent can forward them to Prometheus/Grafana or CloudWatch. There is no scrape endpoint, so nothing new is public.
- The Discord Activity (`api/DiscordActivity/`, frontend `components/Activity/`) is the watch room from ADR-0006. When the app is served from `*.discordsays.com`, `main.tsx` renders it instead of the router. `POST /api/activity/token` trades the Embedded App SDK's code for a short-lived room token, but only after Discord's activity-instances API confirms the user is in that instance, which needs `DiscordActivity:BotToken` (the Activity reports itself off until it is set). Room endpoints require the `Activity` policy (bearer room token), never the site cookie. Room token claims never use `NameIdentifier`, which the rest of the API reads as an account id. The room itself is a SignalR hub at `/api/activity/hub` (`WatchRoomHub`, camelCase JSON, hand-written client types in `shared/services/watchRoom.ts`). Rooms live in memory on the one prod instance (`WatchRoomRegistry`), so a deploy drops them and clients reconnect into a fresh room; running more than one `clips` instance would break rooms. The first member to connect hosts. Any member can queue clips from their own shelf, in round-robin order by who queued them. Only the host plays, pauses, seeks or skips, and reorders, removes or locks the queue; the host's player reaching the end moves the room on. A queued clip is shown only while its owner is in the room: an absent owner's clips are hidden and dropped when their turn comes. Queue items carry no video id until they play. Anyone in the room, guests included, can react to the playing clip with one of a fixed set of emoji (`WatchRoom.ReactionEmoji`, mirrored in `reactionEmoji`), limited per person; reactions go out once on `Reaction` and are never kept. Followers correct drift by nudging `playbackRate` and seek when more than a second out. The hub accepts the room token from the `access_token` query parameter (WebSockets can't send headers); nowhere else does. Room tokens are renewed through `POST /api/activity/token/refresh`, which checks the instance again. Members pick from their own clips (`GET /api/activity/clips`) and the Activity plays the clip through the same `attachStream` as the rest of the site, in its own `ActivityPlayer` because the room drives it. Clips and the playing clip carry `media` (`ActivityMedia`: the host, the video's folder under its media origin from `ClipMediaUrls.MediaPath`, and the stream's type), from which `clipMediaUrls.ts` builds the path: Bunny's HLS playlist under `/bunny-cdn/{videoId}/`, or R2's `av1.mp4` under `/media/clips/{clipId}/v{n}/`. The Discord application's URL Mappings need `/` → the prod site, `/discord-cdn` → `cdn.discordapp.com`, `/bunny-cdn` → `vz-cd8f9809-39a.b-cdn.net` and `/media` → the prod media domain (`R2:MediaBaseUrl`'s host). The Activity is built and tested on prod only.
- Account deletion (`api/Users/AccountDeletionService.cs`, Settings → Delete account) marks the account and removes its identities at once; `AccountDeletionBackgroundService` then deletes its videos at their hosts (Bunny videos and collections, R2 objects) and finally the `app_user` row, which cascades. The job runs only where `AccountDeletion:Enabled` is true (default). Dev has its own database and Bunny videos, so deletion can be tried there.
- The terms of service and privacy policy are `frontend/src/routes/terms.tsx` and `privacy.tsx` (shared layout in `components/Reelshelf/LegalPage.tsx`). When a change collects new user data, sends it to a new third party, or changes retention or deletion, update the privacy policy and its "last updated" date in the same PR.
- Every endpoint must carry its own `RequireAuthorization()`; there is no global auth middleware after the whitelist gate was removed.
- OpenAPI is only mapped in Development, `OpenApi`, or when `OpenApi:Public` is true; background services are disabled in `OpenApi` environment.
- Production image builds the frontend first, publishes the API, installs `ffmpeg`, and serves `frontend/dist` from API `wwwroot`.

## CI / Release

- `.github/workflows/ci.yml` runs on every PR and on pushes to `main`: `Frontend` (`bun run check`), `API` (`dotnet build` + `dotnet test` on `Reelshelf.sln`), and `API client drift` (`bun run check:api-client-drift`). All three must pass locally before opening a PR.
- `main` is protected by the "Protect main" repository ruleset: no direct pushes, force pushes, or deletions; changes land only via PRs with the three CI checks green. Repository admins can bypass only from the PR merge box, and GitHub records every bypass.
- `.github/workflows/publish-app-images.yml` builds GHCR images on `main` changes touching `api/`, `frontend/`, `migrations/`, `Dockerfile`, `package.json`, or `bun.lock`. Its `worker` job builds `ghcr.io/pluscosmic/reelshelf-worker:sha-<sha>` from `workers/Reelshelf.Worker/Dockerfile` (or on dispatch with `worker`); the image's build fails if its ffmpeg lacks libsvtav1, libopus or zscale/tonemap.
- The workflow also opens an infrastructure PR bumping image tags in `PlusCosmic/infrastructure`, closing any older open bump PR. It decides what to build by diffing against the commits of the images currently deployed in that repo's `services/clips.yml`, not the previous push, so a superseded bump PR can't drop a migration; migration changes build the migrations image, and app-impacting changes build the app image. The worker follows the same model: it is built when `workers/` (or the workflow) changed since the `reelshelf-worker:sha-` commit deployed by any infrastructure `services/*.yml` with the worker's image (`reelshelf-worker-dev.yml`, and the prod file once it exists), and the same bump PR rewrites the worker tag in every such file. A failed app build opens no bump PR, as before; a failed worker build only leaves the worker out of it. Runs are serialized.
